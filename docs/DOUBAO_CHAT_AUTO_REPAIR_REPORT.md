## 2. 原来漏接在哪里，本轮如何接通

| 入口／机制 | 原行为及缺口 | 本轮处理 |
| --- | --- | --- |
| 自动收取 | 观察器传 `allowRepair=true`，仍依赖前端 `liveJobs` 等条件 | 主进程返回明确内容修订资格；前端将授权、本次观察与持久化次数分别判断 |
| 用户主动收取 | `collect(jobId)` 的缺省参数为 false，与自动观察入口不同 | 正常收取接入统一结果处理；打开项目及历史预览仍不形成发送授权 |
| 明确继续原任务／批次 | 重开后内存 live 集合不完整，可能只能停在父错误或漏接既有修订 | 沿保存的父子 job 找当前有效修订，连接原 task/run，未决提交只观察 |
| 初次分析、重分析 | 已有候选及 repair；方案校验在首个字段抛错 | 收集能明确诊断的多个问题，修订成功仍返回完整方案候选 |
| 人物／道具／场景与提示词 | 已有专用目标及合同；部分 repair 路径职责继承不完整 | 修订保留原目标、素材类别、模型写法、引用与返回合同 |
| 首帧／尾帧／视频、单项／批量文字 | 已有 prepare、TaskService、网页执行和候选链；父错误与子结果交接不一致 | 共用同一 prepare／启动／绑定／收取／采用链；修订是原目标的内部步骤 |
| 用户明确局部 revise | `canRepair` 和 repair 校验直接排除 revise | 明确的新创作轮次可对其坏回复自动定向纠正一次，不能递归无限修订 |
| 候选采用 | 方案或正文校验失败可能直接冒泡；提示词资格检查会短路明确内容错误 | 采用前完整复核；可修复内容错误回传原候选 job 作为修订依据，旧上下文不发送 |
| 自由 Chat 选择回复 | `applyConversationReply()` 在方案／正文校验后直接抛错 | 单纯预览只读；明确应用选定坏回复才保存独立来源快照、安排一次 repair，修后重新确认 |
| 用户编辑、项目打开 | 不应自动启动 Chat | 保持零自动发送；编辑失败保留草稿，历史合法小数只读保留原值 |

## 3. 内容分类、时长与完整修订请求

明确内容错误使用 `PetStoryContentValidationError`，随错误保存 `code`、`path`、`targetId`、原值、`actualType`、期望约束、`repairable` 和说明。方案校验先聚合独立字段、类型、引用、时长等明确问题，再执行原严格验证。提示词继续复用当前引用、台词、声音格式和模式检查。

只有归属明确、已经完整保存的内容问题才获得自动修订资格。任务／运行归属冲突、错误的字符串 requestId／目标集合、过期上下文、登录、网络、提交不明和磁盘等问题不作为内容改写依据。缺失或类型错误的返回标识属于结构问题；与本次请求发生实际冲突的字符串标识则停止混用。明确的短追问在方案和正文内容校验前识别，需要用户回答，不能因为同时缺引用而自动请模型替用户决定。

本项目新创作方案统一为 **5～10 秒内的有限整秒数值**，与现有视频参数映射一致。数值越界、字符串、null、缺失、非有限值和小数会给出具体证据；不使用截断、不统一填 5、不删除镜头，也不把项目规则写成所有豆包入口的官方限制。

旧工程曾接受 5～10 之间的有限小数。为避免更新后打不开既有项目，read/open 仅允许这些原本合法的历史小数原值读取；不会改数值或发送新请求。写任务元数据时逐值保留原方案和历史候选；新增或改变的方案、采用和生产仍严格验证整秒。异常类型和越界不被兼容为可投产方案。

真实构造的 repair 请求包括：原任务职责及实质规则、当前故事与确认事实、逐字台词、素材用途和参考职责、原创作请求、原回复全文、全部已确定问题、可改字段范围、必须保留内容、新 requestId、精确 targetIds 和完整输出合同。修订纯文字不重复上传全项目图片。原文作为待处理数据保留，程序不补写创作值。

`originKind` 及持久化父链让 repair 继续采用原职责：视频使用视频及对应方言；尾帧使用图片编辑；基础素材使用人物／道具／场景各自规则。显式修订的下一轮也不退化成分析。

每条新回复先保存 `rawText`，再解析和完整复核。方案修订还对照原回复检查无关人物、剧情、镜头顺序、起终、动作和逐字台词。时长问题仅放行该字段及必要节奏说明。无解释的漂移不因 JSON 合法就算成功。确需拆镜或改变锁定内容时，豆包必须在完整结果中明确 `requiresConfirmation=true` 和非空 `changeReason`；保存为需要确认的新候选，原已采用方案保持不变。

## 4. 关联、一次预算、并发、暂停与重开

项目已有 `jobs` 是事实来源，repair 以 `parentJobId` 关联原回复，任务仍由现有 TaskService 建立、提交、回读。自动预算不依赖前端内存集合：普通创作和用户明确的 revise 轮次可以有一个 automatic repair；automatic repair 失败不得再自动递归。用户明确请求的新一轮使用 explicit，保留原失败历史；该新轮次自身仍最多一次自动纠正。

同一父 job 的 prepare 是幂等操作：已保存子任务时返回原子任务标识；同进程并发 prepare 共用同一 Promise，IPC 继续按项目串行。重复收取、组件回调、切页与重开不会创建第二条同父修订。父任务收取后发现已有子任务，只连接该子任务的当前状态，不重新发送原任务。

已排队但确实未提交时，明确继续连接同一保存任务。已有 run、提交意图或提交不确定时只恢复观察／核对，不因超时重发。用户暂停、结束等待或自由交流不授权下一次发送。结束自由调整会标记其尚待修订 job 的 `endedWaitingAt`，后续不能为它绑定新 run。旧回复通过故事、事实、final、已采用帧及前镜边界快照判定过期，不能覆盖新内容。

自由 Chat 使用具体 `reply.key`、前一条用户消息及平台消息标识核对选定来源；不默认取最后一条。坏回复另存为独立 invalid 快照，旧 task/run/rawText 不变。新 repair 的 `repairReplySource` 只关联该快照，不能把选定旧回复冒充为本次新请求的回复。

自由调整保持 active。`chatAdjustment.repairJobId`／`selectedReplyKey` 与源任务上持久化的 `chatAdjustmentGuard.allowedTaskId` 只许可这一个修订任务取得原账号租约，其他账号／任务的保护不解除。重开恢复相同许可；explicit 新轮次也更新相同源保护中的许可。未发送草稿继续由原网页发送点检查，不能覆盖用户草稿来发送修订。

## 5. 修好后返回哪里

当前任务卡按同轮最新子结果投影：修订进行中展示修订状态，父错误留在详情；修订成功后展示对应候选，父旧错误不再成为当前阻断。一次修订仍失败时结束自动链，保留两次原文及原因，现有“在豆包中调整”等入口继续可用。

方案与自由调整结果保留用户确认。未采用前不替换原方案、用户手改 final、已确认图片或已存在媒体。提示词候选仍走对应素材／镜头及 promptKind 的正常采用链；提示词修订不触发生图或视频重生成。

保存的文字批次沿原目标转接其修订 job。修订期间不把父目标算作完成；修订通过后只结算一次。需要采用候选时停在清楚的待确认点；正常采用后才继续已有授权范围，不把待采用当成失败，不自动扩大到新媒体或 P5。
