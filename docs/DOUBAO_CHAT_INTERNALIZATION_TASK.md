## 4. 把Skill转成能直接执行的对话任务

### 4.1 加载创作规则，而不是安装标记

复用当前已移植的规则。规则缺失时查阅公开仓库：
`https://github.com/zenstory-ai/drama-skills`

按实际任务选择对应SKILL与必要references，包括：
- 剧本理解与规范化：short-drama-write中保留用户原文、因果、对白与制作信息的规则。
- 资产分析：short-drama-assets中身份、变体、状态和连续性规则。
- 基础图提示词：short-drama-image-prompts及人物、地点、道具、局部编辑规则。
- 分镜／首尾关键帧：short-drama-storyboard及shot-craft、keyframe-craft、调度相关规则。
- 视频：short-drama-video-prompts、performance-action-timing，以及当前目标对应的方言。
- 局部审查：只加载当前任务相关规则。

保留方法的实质，移除不适用于普通Chat的本机文件读写、Skill调用和供应商执行指令。把“读取某文件”替换成程序提供的实际内容，把“保存某文档”替换成应用需要的返回形式。

不能把几十条实质方法压缩成“你是专业导演，写详细一点”。也不能每次把全部仓库注入。维护简短的“任务类型 → 规则片段”映射即可，不搭建新的Agent框架。

### 4.2 每次请求的稳定结构

请求至少区分以下部分，字段名称可适配当前代码：

1. 本次任务：正在理解剧本、设计分镜，还是写哪一类生成正文。
2. 目标与输入方式：实际选择的模型、模式、时长／画幅、输出语言；未知项如实标识，不硬套版本规则。
3. 创作规则：本阶段实际需要的规则内容，而不是名称或路径。
4. 已确认事实：当前采用的剧本、角色和造型、道具、场景、已有台词。
5. 本次设计输入：镜头目的、起止状态、表演、前后关系与机位要求。
6. 参考清单：稳定素材ID、名称、用途、计划标签、实际可用情况及控制范围。
7. 输出要求：完整自然语言正文和最小必要元数据分开返回。
8. 提交前自检：仅检查本任务的具体规则，在最终回复前修正；不要求输出冗长思考过程。

这是普通Chat消息，不假设存在可设置的API system角色。

每次调用自带必要上下文，不依赖一次“学习Skill”后的聊天记忆。需要分批时由程序带入已保存的确认结果，不让用户复制粘贴上下文。

## 5. 按任务设计不同对话，禁止万能提示词

### A. 剧本理解与镜头设计

- 当前采用剧本是事实来源，旧失败提示词只是问题样本。
- 提取事件因果、人物／道具／场景、已有台词、信息揭示与动作状态。
- 保留主要事件、角色身份和原台词；细化必要构图、姿态、表情与节奏是创作工作，不应被禁止。
- 全场先统一空间及状态关系，再逐镜生成正文。
- 镜头数量动态；用户已确认镜头的局部重写不擅自重拆镜。

### B. 基础素材图片正文

- 人物、道具、场景分别请求适用内容。
- 人物写身份与造型，道具写结构材质尺度，场景写地理布局与光线。
- 不把后续剧情、其他角色动作、制作状态串进素材图正文。
- 未确认的设计作为候选保存在元数据，正文仍写明确可执行的设计；不是把“待确认”等工作说明塞给生图模型。

### C. 分镜首帧正文

- 从已确认起点和本镜可见素材写一个静态瞬间。
- 写清景别、机位、可见部位、人物方位、姿态、表情、视线、手和道具关系。
- 不把整个镜头action或终态拼入正文。
- 终态可以用于内部检查是否提前泄漏，不得成为首帧的正向画面要求。
- 不以“保持一致、自然、电影感”代替具体画面。

### D. 尾帧编辑正文

- 明确以本镜选定首帧为编辑对象；图片未产生时只能是标明输入计划的草稿。
- 让豆包在原回复中写明目标变化、具体终态和必须保留的身份、道具、空间、机位与光线。
- 不能仅输出另一张独立图片的描述，再由代码统一加“以首帧为基础”。

### E. 视频正文

- 同时提供共同的镜头状态、正确参考清单、当前目标模式与对应方言。
- 豆包完成触发、动作过程、可见反应、角色互动、持物操作、原有台词的演绎及结束状态。
- 正文中的手位、持物与站位，和已确认首尾状态一致；需要变化时写出过程。
- 只写该镜需要的声音和动作，不为凑字数加戏；不能所有镜头都套“缓慢自然”。
- 方言对素材、对白、声音、字幕有明确要求时，要求豆包在第一次原回复中执行，而不是留给后处理补。

## 6. @引用必须在Chat生成任务中明确约定

先由程序为本次目标生成任务准备稳定的素材清单，再提供给豆包撰写正文。

清单区分：
- assetId：项目稳定身份。
- 用途：身份、道具外形、场景、首帧、尾帧等。
- 本次目标标签：当前方言要求的@图片N等标记。
- 状态：计划输入或已有真实图片。
- 可参考／不可带入的内容。

要求：
1. 对需要@引用的Seedance方言，明确要求在正文相关位置使用清单标签，不能用“同上”“前图”或只列一遍素材表代替。
2. 对已有明确输入计划的草稿，也能写出计划标签；在元数据标记尚未完成真实绑定，不删除引用，也不声称已上传。
3. 没有图片或确认描述时，不让豆包声称看过图片。身份信息沿用用户确认资料，不由默认预设覆盖当前图。
4. Chat看图附件与最终媒体生成附件可能不是同一顺序；明确给豆包的是“目标生成任务的标签表”，程序维护两者映射，不能混用。
5. 实际上传顺序变化只允许对已存在的合法引用做确定性映射，并在界面展示最终全文。改变素材用途、生成模式或正文语义时，回到Chat重新生成／修订。
6. 真实@节点与首尾槽位继续由现有网页执行层处理，不以文字代替槽位。
7. Seedream使用对应图片入口的引用表达，不把Seedance所有格式机械套给生图。

语法约定来自当前实际采用的规则，不把仓库文法当作所有模型的统一强制协议。目标模型未确定时不能默默按某版写后又宣称专用格式合规。

## 7. 输出约定和自动修订

优先复用现有返回格式，只保留必要信息，例如：
- shotId／assetId、任务类型。
- 完整promptText。
- referenceUsage及计划／已准备状态。
- 本任务确实缺少的输入。

必须把正文保存为完整字符串，保留中文、引号、花括号、@、角括号和换行。HTML展示需要安全转义，但不能删除文本中的模型语法。

不限制固定最短字数，不无证据硬截断，不把详细回复再压成scene+action摘要。

生成后：
- 代码检查引用可解析、所选方言必须的格式、镜头ID、正文非空和字段完整性。
- 内容一致性检查只引用具体冲突，不用关键词计数冒充内容质量。
- 不合格时给豆包发送“原请求要点＋原回复＋具体缺项”，要求重新返回整条合格正文。
- 最多自动修订一次；仍有问题保留候选和原因，允许用户继续，不无限循环。
- Codex和程序不能替豆包补写创作正文来通过检查。

保留用户手改final，新回复进入可采用候选；未手改内容按现有正常规则采用。重开、导出、画布与生成任务读取同一份已采用结果。

## 9. 实施边界与交付

本轮仅修改对话设计、规则选择、上下文准备、必要回读／保存和修订接线。维持原资产确认与媒体执行规则，不新建评分平台、第二套Agent或大规模数据迁移。

交付：
1. 真实根因：哪些要求根本未进请求，哪些是模型未遵循，哪些是读取／解析丢失；没有证据的标为未确认。
2. 实际使用的任务模板和规则映射，可供用户检查；不是只报“内化成功”。
3. 原五镜头13项完整新回复及其采用状态。
4. 简短请求对照：原请求缺什么，新请求如何明确，原回复因此是否改变。
5. 类型检查、构建与相关测试结果。
6. 启动命令、画布查看位置及剩余项。

更新当前OpenSpec与项目进度，保留现有工作树。不自动提交、推送或归档其他变更。无历史开发时限，但不扩大功能范围。

**最终标准：豆包原回复本身就满足当前任务的创作与表达要求；不是由开发者或后处理替它写出一个合格版本。**
