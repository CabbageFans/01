## 3. 必须实现的用户体验

### 自动请求返回不合格内容

用户已启动创作 → 豆包返回 → 保存原回复 → 校验发现可修复错误 → 自动创建一次定向修订 → 豆包返回修订结果 → 完整复核 → 更新同一个逻辑任务的展示 → 回到原有候选确认或后续文字步骤。

用户不需要为第一次自动修订额外点击按钮。

当前错误处理应显示简短状态，例如：

- “正在请豆包修正镜头时长…”
- “已修正，请确认分镜方案。”
- 修订后仍失败：“豆包还未修好镜头时长，你可以继续调整。”

不要先用整页红色横幅宣布最终失败，又在后台偷偷修订；也不要同时显示多个平行失败卡片。

### 用户选择自由对话中的满意回复

用户选择具体回复并点击应用 → 校验发现可修复问题 → 以这条明确选定的回复为依据请豆包整理／修订 → 展示修订后的完整预览 → 用户确认后采用。

选择回复、打开预览本身不发送新请求。将“应用到当前创作”明确设为包含必要的一次格式整理／修订的操作；在用户执行这个动作时交代即可，不增加第二套常驻勾选框。

原回复能直接通过时，不额外请求豆包。

自动修订不得取消原有的用户方案确认和图片确认，不得自动覆盖已采用方案、手改 final 或已确认图片。

## 4. 区分错误，不是所有异常都交给豆包

复用现有结果类型，必要时小范围补充结构化错误。至少能够区分字段路径、目标、当前值、期望约束、问题来源和是否适合修订。示意字段可以是 `code / targetId / path / actual / expected / repairable / message`，具体命名按当前工程风格，不强建通用校验平台。

### 适合自动请豆包修订

- 已确认属于当前请求的回复存在 JSON／结构错误。
- 必填字段缺失、字段类型不符、时长不符合本次项目约束。
- 引用集合遗漏、字段引用错误且正确目标在当前上下文中明确。
- 对应规则要求的素材标签缺失、标签格式错误。
- 已确认原台词漏写，或对应声音格式未遵循。
- 具有明确依据的手位、持物、起止状态等局部冲突。

此处的内容矛盾使用已有校验／内容审查的明确证据，不创建覆盖所有艺术效果的自动评分系统。

### 不交给豆包自动“修复”

- 网络、登录、验证码、免费额度不足、平台入口不可用。
- 尚未取得完整回复、仍在生成、提交是否成功不确定。
- 文件损坏、磁盘写入失败、媒体下载失败。
- 回复账号／会话／任务归属不确定。
- 用户确认素材缺失、需要用户决定角色或剧情。
- 应用自身字段映射、序列化或旧数据兼容错误。
- 用户已经修改创作依据，使旧回复过期。

这些情况走对应恢复或用户处理，不用 Chat 掩盖程序缺陷。无法判定时保留原因，不假标成功。

### 一次反馈完整问题

尽可能收集同一回复内可明确诊断的问题，一次交给豆包，避免“修完时长，才告诉它缺角色字段”。结构无法解析时先处理结构；不能为了收集全部问题移除严格校验。

## 5. 本次时长问题的具体修复要求

1. 取得截图对应的实际原回复、字段路径、值和类型，不能凭截图断定具体数字。
2. 核对生成请求、解析、方案验证、编辑控件、生产参数映射是否使用一致规则。
3. 当前项目若仍规定每镜 5～10 秒，则按该约束修订；不要擅自放宽成其他范围。
4. 5～10 秒是项目当前设计约束，不要写成豆包所有入口的官方统一上限。
5. 若执行层只支持实际可选整秒，核查是否存在“7.5 秒分析可过、生产必失败”的不一致。将明确适用的限制同步给生成任务与校验；网页能力未知时只生成计划稿，不伪造实测支持。
6. 不能程序直接执行 `Math.min/Math.max`、统一改成 5 秒、删除异常镜头，或者放宽类型校验来绕过错误。
7. 修订须兼顾原动作和台词能否在合法时长内完成，保留剧情、身份、顺序、原台词和无关设计。
8. 优先修正原镜头时长及必要的节奏描述，不擅自更换整个故事或重排全部镜头。确实必须拆镜、改台词或改变用户锁定总时长时，生成解释清楚的新候选或请求用户决策，不静默改动已确认内容。
9. 合法类型的无损解析／JSON 围栏提取可以沿用现有实现；不得把代码修改的创作值伪称为豆包修订结果。

## 6. 如何构造给豆包的修订请求

复用当前 `prepareRuntime('repair', …)`、任务服务、网页发送和回读能力。原请求已完成且内容不合格时，修订是一个关联的新文字请求，不是重发原生成任务。

修订请求必须实际包含：

- 当前任务职责及适用的 drama-skills／模型写法规则。
- 本轮新的请求标识和正确的返回目标，不复用旧请求标识冒充原回复。
- 原请求的创作目标与必要约束。
- 原回复原文，不用 Codex 手工润色稿替代。
- 本次校验问题：路径、实际值／类型、期望约束和证据。
- 当前剧本、已确认角色、道具、场景、镜头起终、原台词及相关参考素材。
- 必须保留的内容，以及允许修改的最小范围。
- 对应任务的完整输出契约。

要求豆包返回完整修订后的目标结果，不只回复“已修好”、修改说明或单个字段补丁。计划修订返回完整计划；单项提示词修订返回该目标的完整正文。不同任务不能都套用同一个输出模板。

### 请求组织示意

【任务】修正本次已返回结果中的明确问题，不重新创作整个项目。
【原目标与规则】实际适用的创作约束、模型写法、素材职责。
【原回复】真实完整回复。
【问题】实际目标、字段路径、原值、约束、证据。
【必须保留】未受问题影响的镜头、人物身份、剧情、原台词及设计。
【返回】使用本次新 requestId 和正确 targetIds，返回符合原目标结构的完整结果。

上述只是请求结构，不要在产品中硬编码特定故事、shot_01 或固定错误值。

### 修订任务必须继承正确职责

不能因为 `kind='repair'` 就只加载分析规则：修视频加载对应视频及方言，修尾帧加载编辑规则，修基础图加载该资产类别规则。显式新一轮修订时应找到原始创作职责，不把修订的修订误当成故事分析。

附件和引用计划必须与目标一致；无必要的纯文字修订不重复上传全部项目素材。

修订后执行同等完整校验，并比较无关内容是否被意外改写。计划中的合法关联变化可保留说明；无关剧情漂移不能因 JSON 合法就视为修复成功。

## 7. 覆盖全部正常入口，不只修 collect 的一个分支

统一复用现有“收取／校验／生成修订任务／再校验”的能力，不建立第二套任务服务。以下入口逐个列出当前行为并接通：

| 入口 | 本轮要求 |
| --- | --- |
| 初次分析、重新分析 | 本轮已授权任务取得完整坏回复后，自动定向修订；成功成为同一轮新的方案候选 |
| 人物／道具／场景拆解及提示词 | 继承原素材目标，修订后仍回到该素材，不改全项目 |
| 首帧、尾帧、视频提示词 | 使用各自规则及返回合同，修订结果回到对应镜头与提示词种类 |
| 单项生成与批量生成 | 修订期间原目标不算完成；通过后只完成一次，不把修订任务重复计数 |
| 收取已完成回复 | 不能因为换了一个前端收取入口就无意漏掉本轮自动修订；但只读查看历史不额外发送 |
| 候选采用 | 采用前再发现可修复问题时，进入原目标修订并返回新预览，不让异常只冒泡为全局红条 |
| 自由 Chat 选定回复的应用 | 针对用户选定的具体回复整理／修订，重新预览后确认，不默认选最后一句 |
| 用户直接编辑字段 | 就地解释字段要求并保留草稿；不自动覆盖用户输入。用户要求豆包协助时才转为修订候选 |
| 项目打开、页面预览 | 不因为历史数据异常而自动发送新请求。保留可读内容并给明确恢复入口，不能打开一次就新增修订 |

不得把所有调用都改成无条件自动发送。正确边界是：自动修订属于用户已启动的本轮创作或明确应用选定回复的过程；打开项目、浏览记录、已停止的任务不形成新的发送授权。

### 自由 Chat 与普通修订共用能力，但不混淆来源

普通任务与自由对话回复的来源不同。不能为了复用而改写旧任务 rawText、taskId 或 runId，把自由回复假装成原任务输出。

复用当前选定回复快照／关联信息，记录修订基于哪条回复；必要时以现有 job 的少量字段建立关联，不引入独立会话数据库。

用户自由聊天期间，普通批次不能抢输入框。用户明确执行应用／修订后，允许这个目标的修订任务进入现有会话保护范围；不得清除全部账号保护。若用户仍有未发送草稿，保留草稿并给就地处理，不擅自覆盖。

修订失败或返回预览后，都能回到原会话继续交流，不把账号永久锁住。

## 8. 自动修订有上限，且重开后不会重复发送

每个已授权的创作轮次最多一次自动修订。不要改成失败无限循环。

一次修订仍失败时，保留两个原回复和具体问题，在原卡片提供“在豆包中调整”；主动再次修订可以作为已有次级操作。用户明确发起新一轮时，可以使用新的轮次预算，不应终身禁止该目标再修订。

自动资格、父子任务、已安排修订和修订结果以现有持久化任务记录为依据，不能仅靠 `liveJobs`、`attempted` 等内存集合保证不重发。它们可作运行缓存，不是唯一事实。

必须处理：

- 自动观察与用户点击收取同时发生，最多创建一个修订子任务。
- 前端切页、组件卸载重挂、重复回调，不重复安排修订。
- 修订已排队、已提交或正在生成时，再点击恢复只连接原修订。
- 应用重启后可识别已安排的修订，恢复等待或观察；不自动为旧历史创建新修订。
- 没有剩余自动次数时明确终止自动链，不递归创建 repair 的 repair。
- 修订请求提交不确定时，只观察／核对原请求，不能因超时重新发同一请求。
- 创建了任务但尚未发出、且确实可恢复时，继续同一个已保存任务，不另建副本。
- 用户取消、暂停、结束等待或进入自由聊天时，不继续后台发送。
- 用户改变故事、角色、素材或目标正文后，旧修订只保留历史，不覆盖当前版本。

复用现有互斥、任务台账、父子关系和持久化机制，只补必要缺口，不重写整个状态机。

## 9. 修好以后要接回原流程，而不是换个地方卡住

### 同一轮结果聚合

初次回复和修订回复属于同一个用户创作意图。主界面只显示该轮当前有效状态，原始失败与修订记录保留在详情。

修订成功后清除该轮已经解决的红色错误；父任务历史错误不再被当成当前阻断。不能清掉其他目标或后来出现的真实错误。

### 候选与用户确认

- 方案修好后展示“请确认方案”，不自动代用户采用或批准制作。
- 自由对话修好的内容返回对应预览，用户确认后才采用。
- 手改 final 和当前已采用内容保持不变，直到正常采用流程处理。
- 普通提示词沿当前已确认的采用策略保存／展示，不因本专项给每一项再新增确认步骤；也不借“修订通过”跳过原来已有的确认。
- 图片仍然先候选预览、后人工采用；修订提示词不触发生图或视频重生成。

### 批次恢复

修订作为原目标的内部步骤，展示同一个目标的进度。修订通过后，原目标只结算一次。

有依赖的新候选未采用时，暂停在“待采用”而不是报错，采用后再继续；无依赖且用户已授权的剩余文字任务按当前队列规则推进。不强制重做已经完成的目标。

自动修订暂不能发送时，例如登录失效或账号处于人工交流中，显示“等待登录／等待结束调整”，不能显示“正在修订”却实际上没有任务。

### UI 只做最小调整

沿用获批布局与样式，在当前任务或方案卡替换状态文案。默认不展示 shot_01、字段路径或内部布尔条件，技术详情仍可查看。

自动修订中不新建大型 Alert、菜单、说明区或设置页。第一次可自动处理的内容问题不要求用户再点“检查／启用／授权修订”等一串技术按钮。

## 10. 验证要求：原五镜头与真实修订必须区分

使用用户原故事、原五镜头及当前实际错误相关回复。五镜头只是验收数据，产品不能写死数量、ID、人物动作或错误字符串。

### A. 定位截图原问题

找到对应项目、原始回复和触发动作，记录实际值、校验路径、为什么未自动修订。读不到本机原始数据时，明确记录证据不足，不把离线复现当成截图根因。

不要为了复现而修改用户原项目的方案、时长、采用关系或任务状态。

### B. 离线回归

使用同一原故事／五镜头数据派生技术故障，不编另一个业务故事。至少覆盖：

1. 有效值不触发多余 Chat。
2. 数值越界、字符串时长、null、缺字段及非有限数值能形成准确问题；非 JSON 值仅用于本地类型测试。
3. 多个镜头同时出错时，修订请求包含全部可明确诊断问题。
4. 第一次错误只创建一个修订；修订合格后返回候选并正确接回原流程。
5. 修订仍不合格时停止自动链，给可用的人工调整入口。
6. 原台词、角色或无关镜头被修订意外改动时，不仅因结构合法就通过。
7. 首帧／尾帧／视频／基础素材修订加载正确规则并使用正确目标。
8. 自动收取、用户收取和重复事件竞态不会重复创建子任务。
9. 自由 Chat 选定回复应用失败时有可用整理／修订路径，而非单纯抛错；只打开预览不发请求。
10. 重开、暂停、取消、提交不确定、用户草稿和旧回复晚到均不造成重发／误覆盖。
11. 单项和批次路径计数一致，修订成功不留下父错误阻断，不跳过候选确认。
12. 网络／登录／文件问题不被当成创作内容错误发送给豆包；修订结束释放应释放的资源。

### C. 正常界面与真实豆包文字验证

本轮允许使用已登录免费豆包普通 Chat，进行本专项必要的真实文字修订验证；不自动生图或生视频，不付费，不替用户确认方案和图片。

优先使用真实失败回复，走产品正常修订链路，取得豆包真实新回复并验证“错误 → 修订请求 → 新回复 → 校验 → 候选”。不要由 Codex 改好 JSON 再写回项目。

真实模型不一定每次都生成错误：不要反复诱导模型出错或浪费额度。无法从正常生成稳定复现错误时，采用两层证据：

- 离线测试证明自动触发、单次约束、重开恢复和批次交接。
- 使用真实失败回复，通过正常修订入口证明豆包能够返回合格结果及页面回填。

明确说明第二层不等于已实测首次错误自动触发，不谎称全链均真实通过。没有真实失败回复时继续完成代码和离线验证，留下准确的人工验证步骤。

真实 UI 验收必须通过可见按钮和正常事件入口；允许只读检查数据，禁止以外部直接调用 store/service、注入假回复或编辑 approved/final 代替界面验收。

记录修订前、修订中、成功待确认和失败可继续处理四种状态；不靠测试用例总数证明用户流程完成。

## 11. 交付与停止条件

执行当前工程适用的类型、Lint、契约、相关单元／集成测试和构建；能运行完整验证就记录本轮真实结果，不删失败测试或放松业务校验。

交付实际代码、相关测试和：

`docs/DOUBAO_CHAT_AUTO_REPAIR_REPORT.md`

报告包含：

- 截图错误的实际触发路径和根因；无法核实的部分单列。
- 哪些入口原来会修订，哪些遗漏，本轮具体修复文件。
- 错误如何进入真实 Chat 请求，适用规则和目标如何保持。
- 自动一次、用户主动新轮次、暂停／重开／去重怎样实现。
- 修订通过后候选确认和批次继续的实际行为。
- 原回复 → 具体问题 → 修订请求 → 修订原回复 → 再校验 → 页面结果的本地证据。
- 离线、真实文字、真实 UI 分别验证到哪里；图片／视频未测就不称通过。
- 启动命令及仍需用户处理的事项。

更新当前 OpenSpec 和项目进度，只标记真实完成项。启动普通应用供用户查看，不留下额外远程调试监听。不能保持 GUI 时提供准确命令及状态。

不自动 Git 提交、推送、发布或归档其他变更。修完本专项后停止，不扩展到 UI 重构、全产品重做或 P5。

## 最终验收标准

在用户已发起的正常创作中，豆包返回当前项目可修复的时长／结构／明确内容错误后，工具能自动请豆包修订一次、完整复核，并将合格结果带回当前方案或目标，不让用户自己处理 JSON。

用户只在真正需要创作判断时确认；修订失败时能继续在豆包调整。不能出现“增加了修订按钮但默认仍卡死”“后台创建了任务但前端仍只显示旧错误”“代码直接改值冒充模型修订”或“修好一条又重复发送”的情况。
