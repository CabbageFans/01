# 方案反馈调整流程与验收口径

本次增量适用于方案页及其中完整方案预览。它允许用户直接调整未采用候选，保留现有明确采用、原任务恢复、角色稳定标识及图片采用规则；制作画布中的单项提示词调整不由本增量改动。

## 用户流程

1. 方案页在当前预览方案旁提供“在豆包中调整”。当前预览可以是初次分析候选、后续调整候选或已采用方案，无须先采用。
2. 点击后打开调整弹窗，用户只填写本次自然语言修改意见。弹窗提供取消和提交；空白意见不能提交，取消不创建或发送任务；本页关闭再打开同一基准方案保留草稿。提交失败保留意见，便于修正或继续。
3. 确认提交后，工具保存所选方案的完整快照及本轮反馈，通过正式分析任务提交完整原剧本、所选方案、用户意见和输出格式要求。用户无需复制上下文、编写技术协议或在自由会话里选择 JSON 回复。
4. 原后台执行链负责发送、等待、正式回读与解析。可修复的格式／结构问题携原要求、最新原回复及校验问题继续后台修订；真实登录、验证、平台拒绝、依据变化或提交受理不明不触发格式改写重试。
5. 取得合格结果后显示新的方案候选。用户查看故事、人物、道具、场景和动态分镜后，点击“确认并采用方案”才更新正式方案。生成成功和展开预览都不等于采用。
6. 用户可以继续点击“在豆包中调整”，以本次选中的新候选为下一轮基准。每轮反馈、基准、原回复和结果保留，不能静默退回旧采用方案。

完整方案不显示首帧、尾帧、视频提示词，以及采用／候选／原始正文、草稿、提示词模型、图片引用协议和编辑复核等制作技术字段，也不提供技术 JSON。方案仍显示镜头目的、构图、人物调度、动作、表演、原台词、时长、运镜、声音和连续性等创作内容。

## 状态与恢复

| 状态 | 用户可见行为 | 处理边界 |
| --- | --- | --- |
| 未采用方案或已有采用方案 | 直接打开调整弹窗 | 不以“尚未采用”为由阻止填写或提交 |
| 填写意见 | 取消或提交本轮意见 | 取消、空意见不发送；等待期间保留草稿 |
| 准备、执行、等待或后台修订 | 显示本次真实任务阶段 | 防止重复提交；后台结果不覆盖旧采用方案 |
| 取得新候选 | 预览、确认采用或继续调整 | 不自动采用，不自动生成图片或视频 |
| 普通历史失败 | 保留历史和对应真实错误 | 不把无关失败归为当前调整阻断，不提示先采用 |
| 同账号有活动执行、真实等待或有效任务锁 | 显示“查看占用任务”，定位任务中心里的具体任务 | 保护账号执行，不打开任意浏览器页面，不新建重复请求 |
| 当前短剧关联任务暂停且提交不明 | 显示“查看占用任务”，优先定位本短剧原任务 | 先核对本短剧原结果；不自动重发 |
| 其他短剧或未关联 smoke 的暂停提交不明历史 | 原记录独立保留，不显示为本次方案占用 | 无活动执行和有效锁时，不能永久锁住整个账号 |
| 旧自由会话调整尚未结束 | 提供“结束上一段调整”，保留本轮意见 | 由用户明确结束旧调整，不要求采用旧回复 |
| 真实登录或人机验证等待 | 提供原账号处理及继续入口 | 不自动求解，不切换账号绕过；完成后续接符合恢复条件的唯一原任务 |
| 提交受理不明 | 保留检查原结果入口及真实原因 | 只读核对原请求，不自动发送；显式重发仅遵循既有单次授权规则 |
| 用户停止、依据变更或任务归属异常 | 显示具体原因，保留本轮记录 | 不继续自动修订或覆盖当前项目，不将结果冒充当前合格候选 |

重复点击、响应丢失、切换页面和重开项目均复用已创建的本轮任务及修订链，不重发已有请求。首次发送尚未发生的恢复，仍须经过正式账号、依赖、输入和交互保护门禁；已发送任务只收取原结果。提交结果不明及单次显式重发遵循 [VERIFICATION_RECOVERY.md](./VERIFICATION_RECOVERY.md)。

暂停且提交不明的任务，只有被当前短剧的 `jobs.taskId`、当前制作步骤 `taskId`、任务 `petstory.projectId` 或原运行输入 `petstory.projectId` 明确关联，才构成本次方案反馈阻断。Studio 项目可以包含多个短剧，不能仅凭 `task.projectId === project.studioProjectId` 认定属于同一短剧。同账号的活动执行和有效锁仍跨短剧生效；存在多个真实冲突时，界面优先定位当前短剧关联任务。

## 数据与实现边界

- 调整请求通过 analysis 的 `planFeedback` 接口携带基准方案与反馈，复用现有任务服务、调度、普通 Chat 执行、收取、校验和候选采用；不新增页面脚本发送链，不直接编辑任务文件。
- 请求绑定具体项目、所选方案快照与本轮反馈。采用前仍核对当前项目依据和候选归属；运行中发生剧本或正式方案变化时，保留结果历史并报告实际冲突，不静默覆盖。
- 用户主动内容调整与后台格式修订分别追溯。格式修订沿同一请求事实推进，不能用程序补写的方案、旧缓存或人工 JSON 充当豆包新回复。
- 旧正式方案、未采用候选、原输入、提交意图、各轮回复和迟到结果保留。采用复用现有映射和更新规则：保持角色／镜头等稳定关系，按实际依赖处理影响；旧图片与视频保留历史，不自动替换或删除。
- 界面只显示用户需要的方案和进度。凭据、Session、完整受控请求、内部页面地址及素材绝对路径不进入普通控制输出或验收报告。

## 验收项与记录边界

- 未采用候选能够直接打开反馈弹窗并提交；空意见、取消及重复点击不会产生多次发送。
- 受控请求使用完整原剧本、用户实际所选方案和本轮意见；调整新候选时使用新候选，不能用旧正式方案替换。请求进入既有正式调度，解析／格式修订后只保存新候选。
- 方案预览不出现提示词标题、各版本正文、模型／引用技术字段和 JSON；故事分镜内容可读，旧方案、图片、视频及用户手改保留。
- 用户明确确认才采用，确认之前旧正式方案与素材关系保持；连续调整不强制中途采用。取消、失败、切换页面与重开均不使旧结果被覆盖或请求被自动重发。
- 普通历史错误不显示“请先采用”。同账号的活动执行／有效锁及当前短剧提交不明分别给出真实原因；“查看占用任务”携具体稳定任务 ID 进入任务中心，不直接打开随机豆包页面。无关暂停历史保留独立恢复，不阻断新反馈。
- 离线行为测试、界面验证和真实平台发送／回读分别记录。测试中的模拟 Chat 结果不能证明真实豆包平台已完成登录、发送、生成或收取验收；本文件本身不宣称真实平台链路已通过。

修正范围是按真实活动、有效锁和短剧关联关系选择占用任务，并在任务中心精确定位。无关历史的状态、提交意图和原回复保持不变，不批量清除、取消、重试或标为完成。

重启后的验收采用只读口径：载入原项目和现有任务，核对本短剧原任务仍为已完成且有保存回复；没有新增活动或有效锁时，旧 smoke 暂停记录不得显示为本次方案阻断。若出现真正关联本短剧的待核对任务，应定位其稳定任务 ID，并保留原结果核对入口。仅重启、展开方案、打开反馈弹窗或查看占用任务均不得创建、采用或重新发送请求。

离线回归覆盖上述关联范围、优先定位和记录保留。重启后的界面回显与新反馈的真实平台发送／回读须分别记录；本次只读根因核对及模拟任务测试，不构成新反馈已在真实豆包发送成功的验收证据。

## 2026-11-03 实机验收

在上述只读排查后，已使用当前原项目和账号，通过正式界面提交用户填写的“其他保持不变，整体视频时间控制在15秒”。初始候选为 3 镜头、共 20 秒。新分析被平台受理并保存完整回复；首次返回的 3／4／8 秒未通过单镜时长检查，后台自动完成一次格式修订，取得 5／5／5 秒的完整回复。

实机同时暴露了原格式修订校验的联动误判：修正前两镜后，第三镜为保持原回复总时长而调整的时长与节奏也被当成无关漂移。现仅在方案反馈的分析修订、父回复有明确时长问题、镜头 ID／顺序／数量一致、修后逐镜合法且总时长不变时，允许重新分配时长及相应镜头的节奏；其他剧情、人物、台词和镜头字段仍逐项核对。负例回归继续拒绝总时长、身份、动作、台词和顺序漂移。

加载修复后的程序并重开同一项目后，点击“读取调整结果”对原修订回复重新校验，未创建新请求。原修订已成为合格候选，真实页面显示“3 个镜头……共 15 秒”，并保留“在豆包中调整”和明确采用入口。验收结束时未采用候选，程序停留在方案审阅页。
