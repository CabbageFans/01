## 2. 先定位“短且差”发生在哪一环

追踪一条真实的提示词数据流：

`分镜/角色 → P3优化输入 → 普通Chat回复 → 解析 → optimized/final → UI编辑保存 → P4任务组装 → 实际附件上传 → 网页输入框 → 提交`

先保存可获得的现有样本，不触发新媒体生成。至少检查生图、尾帧编辑、首帧视频、首尾帧视频四种用途；不存在的历史样本标明不存在，可以补离线测试输入，不能伪造生产记录。

重点定位：

- 分镜生成模板是否强迫“一句话”“简短描述”，把动作和角色信息挤掉。
- 角色设定是否只传名称，没有外观、服装、身份、参考图对应关系。
- 优化输入是否缺少 scene、startState、endState、角色站位、动作主体、道具归属及实际模式。
- Seedream和Seedance是否误用同一通用模板。

- 显示、保存、重新打开、单独优化、首次批量生成是否走了不同组装路径。

## 3. 内置“噜噜／噜妹专用角色与风格预设”

### 3.1 预设用途与优先级

本工具面向噜噜、噜妹视频，必须在萌宠短剧流程预先提供专用角色锚点，不能要求用户每个镜头重复介绍两个人物。

使用轻量本地配置及规则文件即可；优先扩展当前角色结构，不建设新角色数据库或训练系统。

分开维护：

- **身份锚点**：角色ID、主体形体、脸部与明显辨识元素。
- **本项目/本场造型**：衣服、帽子、斗篷等当前选定设定。
- **本镜头状态**：动作、表情、视线、道具、站位。
- **共同视觉风格**：材质、光线、背景细节、表演方式。

实际已选参考图定义当前角色的外观，用户明确的修改定义要改变的部分，内置预设只补充未指定项。预设不得与参考图和用户指定造型互相打架。

用户明确让角色换装时，不自动换回默认服装；现有项目手动保存的设定不被启动或迁移静默改写。新草稿默认应用预设；已有项目提供显式优化入口，不自动重新生成素材。

### 3.2 从本样片观察到的默认锚点

以下是本样片的观测，不是对所有作品的官方角色设定宣称。细节以本项目批准参考图为准。

**共同：** 拟人化3D卡通水豚，大头、圆胖身形、短四肢、小圆耳、突出且宽圆的橙色吻部；主体偏浅黄／金黄色。表面细腻圆润，眼睛有明显高光，不是长毛写实棕色水豚。布料有褶皱、环境有真实生活细节、光线柔和，形成卡通角色与生活场景结合的视觉效果。

**噜噜：** 样片约3.4秒、18～26秒可见；头顶完整小橘子及短柄，浅黄身体、橙色宽吻部、大眼睛；白底红草莓图案短裤。默认不凭空加上衣、蓝色背带裤或女生的帽饰。

**噜妹：** 样片约1.8秒、7.7秒、22秒可见；粉色荷叶边软帽、粉色带褶边的衣装；帽顶浅橙色扁平圆环／盘状装饰，上方有双叶绿色嫩芽。不把这个装饰直接写成噜噜的完整小橘子。装饰具体命名不确定，保持图像形态即可，不能臆造精确结构。

**本场造型差异：** 家中约7.7秒披浅黄色柑橘图案斗篷；面馆约22秒没有同一斗篷。斗篷属于场景造型，不能塞进每个镜头的身份锚点。

**本样片表演：** 家中噜妹通过抬下巴、半眯眼、嘴角上扬表现得意；噜噜有疑惑、配合的反应。面馆噜妹通过内收姿态、犹豫视线和委屈表情表现怯场，噜噜侧头关注。迁移的是可见表演方法，不把“永远强势”“永远害怕”硬编码成每个故事的性格。

**场景和配角：** 米色沙发、家居靠垫、木质面馆、面碗、香菜、穿白围裙的牛形店员都只属于相关镜头，不自动加入每个项目。配角不得继承主角头饰或身份特征。

只对本镜头实际出场的人物注入必要锚点，不强制噜噜、噜妹每镜头同框。不把“固定主演”变成“角色最多两个”。

## 4. 参考素材必须有明确用途，不能只拼文件路径

复用现有素材绑定，补齐必要语义；不另建重型资产系统。

内部至少能区分：

- 主演/配角身份参考：定义谁长什么样，不默认复制它的背景和姿势。
- 当前场景参考：定义空间、机位或氛围，不抢占角色身份。
- 本镜头首帧：定义起始构图、姿态、位置与道具状态。
- 本镜头计划尾帧：定义目标终态。
- 上一选中视频实际末帧：用于已批准的continue接力。

内部记录实际角色ID、素材ID、用途、上传顺序或专用槽位。根据真实上传清单生成外显引用，不靠模型猜“图1、图2”。

例如：生图输入为`噜噜、噜妹、场景`时，角色引用与这三张图的用途对应；原生首尾帧视频输入为`首帧、尾帧`时，不得继续沿用“第一张是噜噜肖像、第二张是噜妹肖像”的旧措辞。

一张图片可能同框包含多个角色，允许按实际画面分别绑定，不强制每人一张；但看不清或未提供的外观不能伪称看清。

引用采用当前豆包普通界面实际可理解的表达。`@Image 1`等专用语法只有真实支持时使用，否则采用明确的中文图序与用途。路径文字不是上传；未上传素材不能被写成“参考图中已经提供”。

## 5. 提示词优化分成五个用途，不能用一个万能模板

### A. Seedream：角色参考图生成／整理（仅已有P4需要的场景）

固定角色优先使用已批准图片，不借优化之名替换角色。
已有P4的必要配角补图仍按原流程执行，提示词强调该配角自己的身份特征及项目统一风格，不能套噜噜的橘子、草莓短裤或噜妹帽子。

如有参考图，明确保留对象与允许变化项。角色图不带多镜头剧情，不新增角色训练、多角度生产或候选图库。

### B. Seedream：分镜首帧

用途是生成**一个准备开始动作的清楚画面**，不是把整个视频过程画进一张图。

按需要包含：

1. 实际参考图对应的角色及可见身份锚点。
2. 场景、景别、机位和本镜头出场角色。
3. 人物相对位置、视线、姿态及道具归属。
4. 本镜头的开始状态，不提前画成动作已经完成。
5. 一致材质、光线和必要构图要求。
6. 少量确有价值的保持项，如两角色帽饰不互换、筷子属于谁。

不用“然后、接着、最后”堆三个时间状态；不生成拼图/分格分镜作为单张首帧。输入参考图自带字幕或标题不意味着新关键帧要复刻文字覆盖；不触碰平台生成标识。

### C. Seedream：尾帧编辑

以已选首帧为本次实际编辑参考，描述：

- 哪个角色的哪些姿态、视线、表情或道具状态需要变化。
- 终态应落在哪里。
- 角色身份、当前服装、非目标物体、场景与不应改变的机位保持什么。

不是重写一份独立文生图提示，也不是每次复制完整的角色长介绍。预期变更可能影响的手臂、衣物与遮挡，应允许同步合理改变。

首尾需要保持相同画幅。若剧情确需换场、换机位，不用“其余像素完全不变”制造冲突，也不偷偷把正常切镜改成不合理的首尾插值。

### D. Seedance：首帧图生视频

首帧已给出外观与构图，视频提示词重点描述**从此刻开始发生的动作和表演**。

应写清：

- 以当前首帧为起点，保留图中实际出场角色和关键视觉元素。
- 谁先注意到什么，完成什么主要动作，另一人如何反应。
- 表情、视线、头部、肩膀或短肢的可见变化，而非只有“很委屈、很霸气”。
- 关键物体的接触与归属；双手/爪与道具关系合理，不用人类五指描述强迫改变角色形态。
- 一项合适的镜头意图和结束状态。

单段只承担一个清楚的主要事件；可以有轻量表演节拍，不硬编码三个节拍，也不强制精确到毫秒。节奏依据实际片段时长，不把十几秒剧情硬塞五秒。

不重复整段图片描述去重新设计首帧；不让机位同时“固定、推近、环绕、切特写”。已有分镜需要切镜时按既有机制处理，不擅自拆增镜头。

### E. Seedance：原生首尾帧图生视频

必须与`resolvedMode`及真实首/尾帧输入一致。

提示词明确：

- 首帧中角色、姿态、道具、机位的起点状态。
- 尾帧中目标姿态/表情/道具归属的结束状态。
- 中间用什么连续动作合理连接，而非仅写“自然过渡”。
- 必要保持项及机位变化；没有镜头移动需求时不额外添加。
- 若首尾内容明显不可达或互相矛盾，提示修改端点或分镜，不自动改剧情。

没有原生首尾帧入口时，普通双图参考只能使用对应的参考生成提示词，说明其为起止状态参考，不能声称严格绑定两端。

所有模式继续依赖P4已有真实能力判断，不为了优化接入方舟/即梦API、寻找私有入口或重写模式适配器。

## 6. “懂噜噜噜妹”必须落实为可执行的表演描述

把抽象情绪落成画面动作，但不要每个镜头都机械套完整动作组合：

- 得意：下巴略抬、眼睑放低、嘴角偏扬、姿态放松；按剧情选择必要项。
- 委屈：视线落向问题物品，再转向对方，嘴角下压，身体略内收。
- 犹豫：想朝某方向开口但停住，视线回到熟悉的人，手中动作短暂停顿。
- 配合或疑惑：先看对方，再轻微侧头、眨眼或短暂停顿，不直接变成夸张惊恐。

使用“本角色做什么、对谁、针对何物”的主谓关系，避免多人场景全部写“它”。站位只在本镜头及连续关系内保持，不把噜妹永远在左、噜噜永远在右写成全局规则。

保留原故事的动作与台词意图，不因为套样片就把每个故事改为面馆、不吃香菜或家中称王。

已有分镜台词只按当前真实可用的原生能力处理，明确说话人，保持原文；不新增固定音色、配音、口型系统，不擅自添加旁白、BGM、字幕和台词。没有给定声音要求时不为填模板而编声音。

## 7. 规则输入可以充分，最终生成文本必须聚焦

给“豆包普通Chat优化器”的输入可以包含完整角色档案、规则、分镜、素材用途和模式。

给“生图／生视频入口”的最终提示词只保留本镜头所需内容，不把整套规则和整个剧本都复制过去。

使用现有P3规则资产。允许参考并小范围更新此前已经引入的Seedream/Seedance规则，保留来源许可，不重新安装外部Agent宿主或一整套优化平台。

官方图像指南建议简洁自然语言；约300汉字是相关模型教程的建议，不是本软件统一硬限。不得把它实现成`slice(0, 300)`，也不得反向要求每条至少500字。简单镜头可以短，复杂镜头可以更长，依据必要信息判断。

本轮不以字符数、关键词命中数、“电影级/8K/完美”数量或模型自评分判定质量。

有限的本地检查区分：

- **确定错误**：缺少实际素材、角色引用不存在、模式与素材角色冲突、首尾顺序错误、空文本、实际提交截断。
- **建议检查**：动作过载、表达含糊、冲突运镜等。只有结构化字段或明确文本冲突能证明时才阻断；普通正则不能冒充理解全部语义。

不新增自动反复优化、自动媒体评分和无限抽卡链。必要的普通Chat优化仍由用户现有动作触发，格式修正沿用已有次数上限。

## 8. 优化结果必须进入最终提交，手动编辑必须受到尊重

沿用当前 `raw / optimized / final` 的语义，不重复造一套数据流程。

1. 默认生成的提示词使用新角色与模式规则。
2. 用户编辑的`final`不被后台重新优化或默认预设覆盖。
3. “重新优化”产出候选；用户接受后才更新其手动文本。初次无人手改的草稿可沿现有逻辑自动采用优化结果。
4. 图片、尾帧和视频分别保存最终文本；视频不能错误读取imagePrompt。
5. 上游素材就绪后，根据实际上传清单和`resolvedMode`完成最后引用绑定；这一步只绑定真实输入，不擅自改故事。
6. 最终实际提交的文本必须在现有提示词详情里可查看；不允许用户看见一份，网页发出另一份。
7. 提交前以现有输入回读机制核对全文与附件。仅允许明确的换行规范化；不要折叠台词内容或静默删段落。不一致则未提交并报告，不再次盲点发送。
8. 必要时增加少量字段：实际提交文本快照、引用清单、规则版本、模式。复用项目数据，不把全文与签名地址刷进通用日志。
9. 模式或参考绑定改变后，更新预览并提示当前编译文本已变化；不能一直复用旧图序文案。
10. 在普通Studio而非萌宠短剧的任务中，不强制注入噜噜、噜妹预设。

不能用“已接入GitHub Skill”作为验收，必须沿最终真实发送路径证明正确文本和素材确实被采用。

## 9. UI只做本专项必需的轻量增强

保留已经重构好的页面。

在现有提示词详情/编辑区域按需补充：

- 当前角色预设与本镜头使用的角色。
- 当前实际参考图顺序/用途、请求模式与解析模式。
- 原始、优化、最终文本以及最近一次实际提交文本（已有则复用）。
- 当前选中项的重新优化、接受或保留手改。
- 缺素材或冲突的具体原因。

可以显示字数供诊断，但不做“越长分数越高”的评分条。不新增独立提示词管理平台或再次改版整个UI。

## 10. 必要测试与质量对照

### 10.1 离线测试覆盖

- 噜噜单人、噜妹单人和双人镜头，分别只注入正确身份与素材。
- 固定角色与配角混合，配角不会继承主角橘子/帽子。
- 家中有斗篷、面馆无斗篷，当前造型能覆盖默认；不把场景道具当角色固定特征。
- 只有一个角色出镜时，不强行补出另一个。
- 参考上传顺序变化后，提示词引用正确同步。
- 同框身份参考与多张人物参考均可正确表示。
- 首帧图片描述静态开始状态；尾帧只编辑必要终态。
- 首帧视频与首尾帧视频用不同规则；参考图备选不冒充原生首尾帧。
- `continue`沿用真实选中视频末帧，计划尾帧不串用。
- 用户手改`final`保存、重开、创建任务后仍被使用。
- 中文、多段落、引号、较长文本经过DTO/保存/输入回读不被截断。
- 缺优化结果、优化解析失败时不静默回退到“可爱水豚做动作”等短空泛模板并标成功。
- 校验正常短提示词可通过，冗长但角色错绑的提示词不能靠长度通过。
- 普通Studio任务不受专用预设污染。

使用样例fixture与mock检查组装、绑定和实际发送前的数据。不得伪造“豆包已返回”“视频效果提升”等线上结果。

### 10.2 必须提供的前后对照

至少形成以下四组可阅读的对照：

1. 在家得意表情的噜妹：参考图生首帧。
2. 面馆双人反应：参考图生首帧。
3. 同一面馆动作：首帧图生视频。
4. 同一面馆动作：首帧＋尾帧的视频及尾帧编辑提示词。

每组列出：实际或明确标注的测试输入、角色/参考用途、模式、原提示词、新提示词、具体补足的信息、最终提交读取路径。没有真实旧样本时写“离线示例”，不得称为从生产记录提取。

开发阶段不自动消耗用户生图、生视频免费额度。普通Chat或其他真实请求按已有授权边界执行；没有明确授权就只做离线测试，用户后续手动验证。

用户手动比较时固定分镜、参考图、模型和规格，优先比较身份、动作、道具、表演与终态。模型具有随机性，少量样本不能证明稳定提升百分比；不建设本轮外的大规模AB平台。

## 11. 范围与交付

允许修改：专用角色/风格预设、现有P3优化规则、必要上下文字段、模式化提示词组装、P4最终输入接线、现有提示词详情和相关测试。

不做：P5合成、配音、固定声线、字幕编辑、音乐、视频发布、新角色库、模型训练、第二套生成执行器、再次全站UI改版、自动质量抽卡或插件市场。

按照以下顺序直接实施：

1. 保存现有提示词样本并定位真实根因。
2. 增加角色/风格预设与实际参考用途绑定。
3. 优化图像、尾帧、首帧视频、首尾帧视频模板和普通Chat优化输入。
4. 接通最终文本与实际发送路径，保护用户手改与旧项目。
5. 补必要界面信息，执行相关测试、类型检查和构建。
6. 写简短前后对照，启动现有应用供用户手动看效果。

交付：

- 真实代码和规则资产，不是只有一份建议文档。
- 当前OpenSpec任务的真实完成状态，不修改旧P5/P6完成状态。
- `docs/PROMPT_QUALITY_REPORT.md`：根因、改动、四组对照、测试、未测能力和手动验收方法。
- 准确启动命令；无真实视频测试时明确“提示链实现与离线测试通过，生成效果待用户确认”。

最终验收问题：

> 换一个剧情以后，工具是否仍然知道噜噜和噜妹分别是谁、素材分别约束什么、图片该画哪个时刻、视频该怎样演、首尾怎样连接，而且用户查看的最终提示词确实就是传进豆包的内容？

完成本专项后停止，不自动继续P5、归档其他变更或提交推送。
