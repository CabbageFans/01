# 短剧工作室前端 UI 统一设计提案（评审稿）

> 仅供设计评审，不修改产品源码、不运行产品测试。配套 `PetStory_UI_Design_Concept.html` 是可点击的静态视觉提案，所有数字、卡片和图片均为示意，不连接后端。


## 0. 本次评审已确认的产品范围与文案要求

- 产品名称统一为 **短剧工作室**；创作功能名称统一为 **短剧创作**。
- 页面主标题使用 **创作工作台**，不显示“UI 提案”等设计阶段字样。
- **彻底移除通用创作功能入口**，包括导航、总览按钮、独立页面、空状态引导和快捷入口。任务中心中只保留短剧创作及其实际相关任务。
- 所有用户可见文案必须从用户目标、当前内容、实际进度和下一步操作出发。禁止出现面向开发者的解释性标语，例如“让用户不必理解内部状态机”“系统按需要你做什么组织任务”等。
- 用户可见文案使用自然、直接的表达，例如“待处理事项”“请确认基础素材”“豆包回复尚未收取”“继续制作关键帧”。不向用户解释内部架构、组件职责、实现方式或开发取舍。
- 本轮仍是设计确认阶段，不修改产品源码。Codex 先通过 Product Design 完成视觉与信息架构优化，展示给用户确认；用户明确确认前，不实施到正式应用。确认后的设计规范作为 UI 冻结基线，后续开发只改业务逻辑，不得自行改动布局、色彩、字体、间距、按钮规格、文案或信息层级，除非用户明确授权。

## 1. 源码走查结论

- `src/App.tsx` 承担应用壳、导航、浏览器宿主和工作区切换；`src/styles/global.css` 仍保留旧的全局主题与按钮样式。
- `PetStoryPanel.tsx` 同时承载故事输入、流程阶段、方案、素材及高级编辑；`PetStoryCanvas.tsx` 又提供全景画布、素材与控制插槽。
- `PetStoryMaterials.tsx`、`PetStoryCanvasPrompt.tsx`、`PetStoryCanvasMedia.tsx`、`PetStoryRuntime.tsx`、`PetStoryTaskRecovery.tsx` 分别展示素材、提示词、媒体、Chat 来源和恢复动作。能力分散在组件里，用户容易看到重复或技术型入口。
- `PetStoryCanvas.tsx` 中素材／控制区域默认关闭；重要入口可能藏得太深，而生成入口检查、素材确认、提示词生成、媒体制作又存在真实前置关系。
- `WorkspaceOverview.tsx` 同时展示 短剧项目、当前短剧、待处理事项；需要清晰区分通用项目与本地短剧项目。
- `PetStoryResults.tsx` 已能展示逐镜本地媒体、文件校验和正文匹配，应继续作为真实成果页。
- `docs/USER_JOURNEY_REPAIR_REPORT.md` 记录了六阶段流程，但也明确真实图片接受、媒体生成和下载仍需用户实测。UI 不应把“代码存在”显示成“任务完成”。

## 2. 设计目标

1. 一个区域只突出一个主动作；同级次要操作最多两个，低频动作进入“更多”。
2. 所有按钮遵循统一尺寸、间距、圆角和层级，不出现同一工具栏内大小、粗细、颜色各异的按钮。
3. 任何阻断都在当前上下文说明原因，并提供直接定位缺项的操作。
4. 六阶段是导航与状态展示，不是要求用户逐页点满的机械向导；已有数据可以跳转查看。
5. 保留画布全景，但普通用户的默认流程由六阶段组织。
6. 提示词生成、图片生成、视频生成、下载、文件校验、人工质量确认分别呈现。
7. 任务ID、运行ID、规则文件、完整请求和原始回复保留在诊断详情，不作为主要用户操作入口。
8. 本轮只设计视觉和信息架构，确认后再分批实施。

## 3. 统一视觉规范

### 色彩
- 主背景 `#F4F6F8`；面板 `#FFFFFF`；次级背景 `#F8FAFB`。
- 正文 `#202A35`；次级文本 `#697584`；辅助文本 `#98A2AE`。
- 唯一主品牌色：深青绿 `#087F72`；hover `#066B61`；浅色状态底 `#E8F5F2`。
- 等待／提醒：琥珀色 `#9B610C` 配浅底 `#FFF4DF`。
- 错误／危险：`#B42318`，只用于真正失败和破坏性操作。
- 不再同时使用紫色流程大卡、青绿画布、蓝色按钮等多个竞争性强调色。

### 字体与间距
- 页面标题 24–26px，600–750 字重；区域标题 13–15px，700 字重。
- 正文 13–14px；辅助说明 11–12px；状态标签 10–11px。
- 页面最大宽度约 1440–1500px；宽屏左右留白 28–32px。
- 面板圆角 12px；输入与按钮圆角 8px；状态标签圆角 6px。
- 卡片内边距 16–20px；卡片间距 14–16px；字段间距 14–16px。
- 采用 1px 中性边框和极轻阴影，不用厚重阴影、渐变边框或大面积彩色背景。

### 按钮系统（必须统一）
- **主按钮**：高度 36px，最小宽度 96px，主色实底；每个主要区域最多一个。
- **次按钮**：高度 36px，白底中性边框。
- **小按钮**：高度 30px，仅用于卡片内操作；同一行规格一致。
- **文字／图标按钮**：高度 30–32px，用于低频操作或紧凑工具栏。
- **危险按钮**：白底红字红边，放入“更多”或确认弹窗。
- 不允许原生浏览器按钮与 Ant Design 按钮混用；不允许一行混用 28、32、36、42px 多种高度。
- 不在一张卡片同时放“生成、全部生成、重新生成、继续、补齐、导出、诊断”等同权重按钮。保留一个主动作，其余按上下文收进“更多”。

### 表单与状态
- 输入框高度 38px；文本域有稳定最小高度和清晰标签。
- 禁用主操作必须伴随可读原因及就地处理按钮，不能只有灰色按钮。
- 状态标签统一为：待开始、进行中、等待你操作、已收取、待采用、已确认、失败、已校验。
- 免费额度只显示页面观察／未知／本地预测，不伪装成平台官方剩余额度。

## 4. 应用全局结构

### 左侧导航（约 220px）
**工作区：** 工作台总览、短剧创作。

**生产管理：** 任务中心、素材与下载、账号与浏览器。
**系统：** 设置与诊断。

导航项统一 40px 高，图标 16px，文字 12–13px。当前项使用深青绿低饱和背景，不使用多种彩色图标。账户信息放在底部。

### 顶部上下文栏（60px）
左侧只显示当前位置／面包屑；右侧显示当前账号状态、帮助入口和必要页面操作。不要重复显示项目路径、项目名、账号名、浏览账号、执行账号等多排胶囊标签。

### 页面头部
左侧标题与简短说明；右侧一个主动作与至多两个次动作。项目路径、执行账号等元数据放在一行简洁信息中，低频操作进入“更多”。

## 5. 页面设计

### A. 工作台总览
- 顶部：标题“创作工作台”＋一句用途说明。
- 主要入口：`新建短剧项目`（主按钮）。
- 中部只保留继续创作、待处理事项、最近项目。统计卡只在确实帮助决策时出现，不做装饰性大数字。
- 当前短剧卡显示名称、当前阶段、完成／待确认数量和唯一“继续当前短剧”按钮。
- 待处理事项使用用户语言，如“需要确认基础图片”“豆包回复待收取”，不显示内部 jobId。

### B. 短剧创作六阶段
顺序：输入剧本 → 确认方案 → 准备基础素材 → 制作关键帧 → 制作镜头视频 → 查看成果。阶段导航约 44px 高，当前阶段白底卡片＋青绿色编号；完成阶段用勾选和低饱和色。不能用大面积淡紫色包裹整个流程。

每阶段统一：阶段标题＋一句目标；一条当前状态说明；主工作区；底部固定操作栏（当前状态／阻断原因在左，返回与唯一主动作在右）。仅在确实不能继续时禁用主按钮，并提供直达缺项的按钮。

**阶段1：输入剧本**
- 主卡为完整剧本原文、大文本框、保存并分析。
- 右侧次卡为默认角色（噜噜、噜妹）、视觉风格、可选参考链接。
- 抖音链接提取为次要路径，不与直接输入剧本并列成两个复杂流程。
- 明确说明保存并分析会调用豆包 Chat；保存失败不发送。

**阶段2：确认方案**
- 展示故事梗概、关键事件、原台词保留情况。
- 展示动态分镜列表：镜头目的、景别、时长、起止状态。
- 候选有明确“采用此方案”；采用后才显示“确认方案并进入基础素材”。不展示生图、视频或诊断操作。

**阶段3：准备基础素材**
- 顶部显示人物／道具／场景真实确认进度。
- 使用“全部／人物／道具／场景”筛选，不堆彩色分组卡。
- 每张素材卡结构一致：素材名与类型、提示词、当前图片、状态、一个主操作。
- 无图片时主操作为“生成图片”或“上传图片”；有图未确认时为“查看并确认”；确认后显示“已确认”。提示词生成与生图分开。
- 全部基础图确认后才出现“进入关键帧制作”。

**阶段4：制作关键帧**
- 左侧镜头列表；右侧当前镜头详情。
- 当前镜头内展示首帧、可选尾帧、参考素材清单。宽屏可三列，窄屏改为纵向卡片。
- 首帧／尾帧提示词、实际图片、状态分别显示；没有图片不显示假缩略图。
- “生成提示词”与“生成图片”严格分开；图片逐张确认。
- 关键帧就绪后提供“进入镜头视频”。

**阶段5：制作镜头视频**
- 镜头列表＋当前镜头视频详情。
- 显示首帧／尾帧引用、模型／模式、时长和完整 Seedance 正文。
- 主操作为“生成此镜头视频”或“生成已就绪镜头”，不同时暴露多个同权重批量按钮。
- 缺素材、首帧、尾帧或入口检查等条件在当前卡片就地显示，并有直达入口。
- 生成、下载、文件校验、人工质量确认分别显示。

**阶段6：查看成果**
- 按镜头列出真实首帧、尾帧、视频、本地文件位置、文件校验、提示词匹配和人工质量状态。
- 缺少产物时显示“尚无本地文件”和“去制作此项”。
- 不出现“整片已完成”或“导出完整短剧”，因为当前范围不包含 P5 合成。

### C. 画布全景
- 保留 ai_story 式横向画布，作为高级查看方式，不作为新手第一入口。
- 工具栏只保留适应画布、缩放、定位当前镜头、切换全景／关键帧／视频。
- 节点列标题固定为故事与方案、分镜、关键帧、视频提示词、视频产物。
- 每个节点只放该对象相关操作；完整提示词可放大编辑。
- 低频控制放进“制作设置”；关键前置项必须在当前节点显示。
- 不在画布主操作区重复显示全局任务诊断、规则文件、运行ID等技术细节。

### D. 任务中心
- 默认分区：待处理、进行中、排队中、已完成／历史。
- 每条任务展示任务名称、当前状态、下一步动作。
- 失败、待验证、回复未收取的恢复入口直接可见。
- 完整请求、原始回复和任务编号放入诊断详情。
- 不把所有技术状态塞进密集宽表；批量操作仅在选中多项后出现。

### E. 素材与下载
- 两个页签：短剧素材、下载记录。取消通用创作后，不再显示通用 Studio 产物入口。
- 素材卡统一缩略图、名称、类型、关联镜头、确认／校验状态。
- 下载失败按钮明确叫“重新下载”，不叫“重试生成”。
- 远程地址有效、已下载、本地文件校验通过、人工质量合格分别展示。

### F. 账号与浏览器
- 左侧账号列表；右侧常驻浏览器。
- 账号状态、登录／验证提示、当前执行账号和浏览账号清晰区分。
- 账号置顶、删除、冷却等低频操作放入行内“更多”。
- 浏览器工具栏统一 32px 图标按钮，不混用大小不一的原生按钮。

### G. 设置与诊断
- 常用设置：下载目录、并发、生成前确认。
- 数据维护：备份／恢复、完整性检查。
- 诊断：日志、页面自检、适配规则、诊断包。
- 常用偏好与开发排障分区，不让普通用户首页就看到规则版本、JSON 和内部ID。

## 6. 按钮删减原则

不是删除功能，而是删掉重复入口与同权重按钮：
- “输入项目路径”与“打开项目目录”如功能重叠，主界面只保留“打开项目目录”；手动路径输入收进次级方式。
- “生成全部提示词”应按实际范围改名，例如“生成缺失的镜头提示词”；基础素材提示词单独操作。
- “继续／补齐／全部生成／重新生成”不同时放在同一主区域；根据当前状态推荐一个动作，其余放入“更多”。
- “打开豆包账号”“打开浏览器”“展开浏览器”如最终调用同一动作，只保留一个主入口。
- “查看原始请求／原始回复／规则来源／任务ID”保留在诊断区，不放在普通流程主卡。
- “检查入口”不应作为独立流程页；当生成被阻断时，在当前卡片显示原因和“检查豆包入口”。
- 不要在同一页重复显示项目名、账号名、路径、项目状态等信息；选择一次，其他地方只显示必要摘要。
- 不删除高级能力；将其归入高级编辑、批量与模板、诊断与维护，避免初次使用者被打扰。

## 7. 交互规则

- 所有页面使用同一套按钮组件和状态标签；禁止页面自定义一套按钮尺寸。
- 主操作有明确动词和对象，例如“确认方案并进入基础素材”，不要用含糊的“继续”。
- 阻断提示采用“原因＋下一步”，例如“缺少已确认的场景图 → 去确认场景图”。
- 用户切阶段、打开项目、展开详情不应暗中触发生成。
- 保存、采用候选、生成提示词、生成图片、生成视频、重新下载必须是不同操作。
- 任何状态必须来自真实项目数据；设计稿里的数字和缩略图仅用于视觉评审，不能直接当产品占位内容。

## 8. 实施边界与评审流程

本稿仅用于先确认 UI 方向。此时不要修改源码、不要跑测试、不要改变任务状态。

用户确认视觉方向后，再由 Codex：
1. 将设计系统落实为共享 token 和按钮组件。
2. 按应用壳 → 总览 → 短剧六阶段 → 任务／素材／账号／设置的顺序改版。
3. 保留现有业务调用和状态机，前端只重新组织入口与反馈。
4. 最后再按用户真实操作路径做交互验收；不要把静态页面存在按钮当成流程通过。


## 8. 用户可见文案审查

- 文案直接说明用户正在编辑的内容、真实进度、具体问题和可执行操作。
- 禁止在界面中出现面向开发人员的产品设计标语、架构解释或自我辩护，例如“让用户不必理解内部状态机”“按需要你做什么组织任务”等。此类文字只允许出现在内部设计讨论中，不能出现在原型或正式产品。
- 避免“只读核对”“状态机”“运行时”“promptTask”“final”“原生发送”等内部术语。根据实际行为改写为“检查回复”“查看生成结果”“请在豆包中点击发送”等用户能直接理解的表达。
- 不在正式产品界面显示“UI 提案”“设计提案”“示意数据，不连接后端”等设计评审说明。静态原型的非真实数据提示放在评审文件说明中，不混入正式界面设计。
- 所有按钮使用同一套尺寸与视觉层级；重复入口合并，低频操作收进“更多”。不得为了展示功能而添加不必要按钮。

## 9. 设计确认与 UI 冻结

1. 当前阶段只产出 Product Design 设计方案与静态原型，不修改正式产品源码。
2. 通过 Product Design 对当前设计进行优化，展示方案后等待用户明确确认。
3. 用户确认后，将获批的颜色、字体、间距、按钮、导航、页面布局、文案和交互呈现整理为冻结规范。
4. 后续开发任务不得擅自更改 UI 视觉和信息架构。业务逻辑可以在既定 UI 内实现；若实现确实需要新增或调整界面，必须先取得用户明确授权。
