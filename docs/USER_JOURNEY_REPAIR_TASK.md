## 3. 已发现的用户流程问题：逐项核实、修复

下列是当前审核发现的机制问题，不是要求对某个测试故事写特殊分支。

### UX01：新项目入口有隐含前置条件

当前新建短剧依赖全局已选账号及 Studio 项目，用户经常要先去“账号与浏览器”再回来；主界面同时展示 Studio 项目和本地短剧目录，容易混淆。

修复：
- 在“新建萌宠短剧”正常入口就显示执行账号、保存位置和关联 Studio 项目。
- 未选账号时提供同处选择／添加／去登录入口，返回后保留新建内容和目标步骤；不要只报“请先选择账号”。
- 已有默认 Studio 项目可复用，但明确显示关联关系，不要求用户先理解两套数据模型。
- 当前短剧绑定账号与正在浏览的账号分开标识。打开豆包或处理任务时定位正确绑定账号，不因浏览其他账号而暗中改绑。
- 不新增项目数据库或另一套账号管理。

### UX02：直接输入剧本与手机提取流程混在一起

当前页面虽然支持无链接输入，却先展示手机提取说明、复制手机提示词、保存链接等内容。用户已有剧本时仍被旧流程干扰。

修复：
- 默认入口“直接输入剧本”；“从抖音链接辅助提取”作为另一种明确可选输入方式。
- 直接剧本模式不要求保存链接，也不因可选链接的未保存草稿锁死剧本保存。
- 直接模式显示完整原文框、制作演员摘要和一个明确主操作，例如“保存并分析剧本”。
- 主操作先可靠保存，再调用现有分析服务；保存失败不发请求。点击该按钮才授权文字创作，切页／输入文字／打开项目不自动发送。
- 用户不必填写 JSON、内部ID、规则版本。复杂演员预设可以展开，但默认主演和可选配角的含义要清楚。

### UX03：新生成方案后没有自然进入结果确认

当前 stage 主要由用户手动切换；打开有 plan 的项目直接进入画布，新项目同一ID生成 plan 后却不会自然进入结果区。结果候选及采用按钮另在画布故事卡内，首次用户不易发现。

修复：
- 分析中在当前页显示目标、进度和正在等待谁；完成后主动呈现本次结果与明确的下一步。
- 展示故事理解、来源角色到制作角色的对应、人物／道具／场景数量、分镜摘要。
- 未采用方案先提供“采用此方案”；采用之后再确认用于制作。不要把“收到回复”“采用方案”“确认制作依据”合并成假成功。
- 用户的一次明确“确认方案并进入素材准备”可以顺序调用现有必要服务，但不得跳过真实条件，也不自动生成媒体。
- 失败或结束等待后，重新分析入口仍要合理可达，不能仅因历史存在一个 analysis 就永久禁用当前页，而要求用户去别处找同功能按钮。
- 无 plan 时，不能出现“保存当前故事”按钮点了内部直接 return 的假动作；初始画布要引导输入／分析，或不展示不适用操作。

### UX04：画布与旧四阶段形成两套操作路径

当前“分镜生产画布”和“故事输入／角色与草稿分镜／基础素材与制作准备／制作进度与素材”并列，很多同功能入口有不同条件，用户需要猜应该在哪套页面操作。

修复：
- 建立一条明确主路径，见下一节。保留画布，不再重做所有页面。
- 现有旧表单有必要的编辑功能就迁入当前阶段／同页抽屉，或保留为明确的高级编辑入口。
- 正常从头制作不依赖用户在两套主流程之间跳来跳去。
- 故事和资产编辑用同一数据源；同一对象不要同时挂两份用户看不见但能互相锁住的编辑草稿。
- 画布负责查看镜头、提示词和产物，不独自承担所有入门、配置、错误恢复功能。

### UX05：多个“生成／继续”按钮职责不清

“生成全部提示词”实际只包含镜头正文，不包括基础素材正文；与“继续／补齐当前阶段提示词”“生成全部基础素材提示词”并列，用户无法预测点击会发生什么。

修复：
- 主要位置只保留当前阶段一个明确推荐动作，按钮名称说明对象和数量。
- 例如“生成缺失的基础素材提示词（7项）”“生成缺失关键帧提示词（8项）”“生成视频提示词（5项）”。数字动态计算，不能写死。
- 批次内明确每项状态：待创作、等待发送、生成中、已保存、待采用、需处理；阶段名称和剩余内容持续可见。
- “重新生成全部”放入次级操作，明确覆盖范围、保留手改以及会重新发起哪些请求；不能伪装成无副作用的“下一步”。
- 已完成且符合当前要求的项目默认复用。手改的新候选尚未采用时，准确显示，不把收到候选当完成全部目标。
- 普通用户不需要知道该点 continuePromptStage 还是 regenerateAllPrompts。

### UX06：素材图生成被另一区域的检查卡住

素材生成按钮依赖当前会话入口检查，检查按钮在默认收起的制作控制中。部分提示只说去顶部找，但没有直接到达或处理入口。

修复：
- 基础素材阶段本身展示素材清单、提示词、当前图片、确认状态和缺失项。
- 缺少剧本确认、正文或入口检查时，直接在当前操作旁显示原因及对应操作，不仅灰掉按钮。
- “检查豆包入口”可在这里直接调用现有能力检查，检查结果回到发起的素材／节点。不要要求用户先进入视频页面才能开始生成第一张基础图片。
- 图片能力与视频能力按当前动作区分；写文字不应先过所有视频控件检查。
- 提供“生成缺失图片”“上传已有图片”“查看并采用这张图片”，生成后保持在当前素材位置。
- 图片显示出来不等于用户确认；不得批量伪造 approved。已确认且未变化的素材不反复要求确认。
- 同类素材卡按人物／道具／场景分组，显示“已选/已确认/仍缺失”数量；完成后有“进入关键帧制作”而非让用户自行找导航。

### UX07：关键帧和视频按钮没有完整解释前置条件

当前节点主要按 busy、dirty、waiting、入口是否检查进行禁用，其余条件常在点击后才由后端报错；关键帧生成、视频模式设置和高级镜头编辑又散在不同页签。

修复：
- 每个镜头卡显示当前有效正文、素材、首帧、尾帧、视频状态；允许展开具体引用。
- 视频生成前缺首帧就直接给“去生成本镜首帧”；首尾帧模式缺尾帧就给“去生成本镜尾帧”。点击定位或切换至真实对应控件，不是静默创建所有前置媒体。
- 请求模式、实际可用模式、时长设置在当前镜头可读且可修改（沿用现有权限）。普通名称为“首帧／首尾帧／多参考”，内部英文值放详情。
- 自动模式仍显示解析结果和必要备选确认，不把普通两图参考包装为原生首尾帧。
- 使用主进程既有资格判断结果作为依据；前端仅映射成用户文案与操作。不能复制一份不一致的正则校验或另一套工作流状态机。
- 所有正文与来源、素材确认等约束保留，但在发送前主动告诉用户怎样满足。
- 图片、视频、提示词重新生成和重新下载保持不同操作，避免误消耗额度。

### UX08：错误恢复藏在“来源记录”折叠区

读取原回复、继续未发送任务、结束等待等操作目前混在任务ID、runId、规则文件和原始JSON附近。业务卡只有“待回读”等技术标签，用户不知是否要等待、发送还是重试。

修复：
- 增加固定的当前任务处理区，显示“正在处理哪个素材/镜头、当前状态、用户需要做什么”。
- 必要恢复按钮直接出现在对应对象和全局当前任务区。完整日志、raw、ID仍可查看，但移入诊断详情，不能成为继续工作的必经页。
- 不变更实际发送事实。用户正常等待、尚未发送、已发送等待回复、待核对、内容需修订，分别说明。
- 不确定提交保留“不重复发送”；提供打开对应豆包会话、检查原回复、结束等待等已有真实处理能力。
- 用户结束等待不是取消平台任务，也不是采用成功。无关目标能继续时给“继续其他可制作项”；相关失效目标保持待处理。
- 不以删任务、改JSON、强行标成功或解除账号租约来解决UI阻断。

### UX09：未保存状态跨隐藏页面影响所有操作

当前 dirty/profileDirty/canvasDirty/sourceDirty 等会共同禁用操作。用户可能在隐藏表单改了一个字段，回到画布只看到“有未保存内容”，却不知道在哪里保存。

修复：
- 待保存提示必须标出对象及位置，提供“保存并继续”“查看修改”“放弃本次修改”。
- 保存复用原来的单对象／版本校验，不能提交一份过期整项目快照覆盖新回复。
- 跨阶段导航时保留草稿或提示处理，不静默丢失，不永久锁死其他无关操作。
- 编辑锁、运行锁、未保存阻断分开；暂停／打开原会话／读取结果等恢复动作不能因为不相关编辑锁而全部不可用。

### UX10：完成标签使用了错误的范围

总览当前只根据 production.state === complete 就显示“镜头素材已完成”，没有区分基础素材批次、单镜头节点和整个项目。

修复：
- 项目完成度从当前方案所需的目标和实际有效产物计算，不能用最后一个批次 complete 代表全片。
- 基础素材完成、提示词完成、关键帧完成、视频下载完成、文件校验通过、人工质量确认分别展示。
- 最终页可见所有镜头的视频／关键帧、缺失项、继续制作入口和实际文件位置。
- 当前只交付逐镜素材，不出现不存在的“完整短剧导出／成片完成”。
- 复用已有文件定位／下载能力；如缺少定位入口，仅补最小IPC，不开发拼接、ZIP打包、剪辑时间线或P5。

### UX11：测试文案和工程术语进入产品主界面

例如运行时面板出现“原五镜头回归应保留候选”等针对测试的文案，以及 final、pending、bound、合同、stage 的工程表达。

修复：
- 测试说明只留测试和开发报告，不展示给普通用户。
- 页面使用“当前使用的提示词／新候选／图片待确认／正在生成／需要处理”等清楚文案。
- 技术信息保留到展开的诊断详情，便于排障，不删除其记录。

## 4. 主流程的明确组织

使用现有真实项目状态派生六个可见阶段，不新建另一套持久化生产状态：

1. **输入剧本**：新建/打开短剧，选择账号，直接粘贴剧本；可选链接辅助入口。
2. **确认方案**：查看本次理解、角色对应、资产清单和动态分镜；采用需要的候选并确认制作依据。
3. **准备基础素材**：生成/编辑素材提示词，生成或导入图片，查看并确认人物、道具、场景。
4. **制作关键帧**：看到动态镜头，写首帧/必要尾帧提示词，生成并选用图片。
5. **制作镜头视频**：按当前真实模式、时长和确认素材生成视频，显示等待、下载与校验。
6. **查看成果**：逐镜视频和图片、缺失项、下载位置、继续任务。不是整片合成。

具体要求：
- 顶部始终回答三件事：现在在哪一步、已经完成什么、推荐下一步是什么。
- 阶段不是必须点满的向导：有有效历史成果就定位合理的未完成阶段；允许查看已完成和后续草稿，不因为顺序展示而添加无关门禁。
- 返回已有项目时定位首个需要用户处理的事项或最近操作位置；不简单用“有 plan 就进画布”。
- 步骤完成后显示明确成功反馈及下一步入口。异步完成时若用户在编辑其他内容，不强制跳走；显示“方案已就绪，查看结果”。
- 继续保留画布全景访问，用于对照所有提示词和素材。阶段视图与全景共享真实组件/服务/数据，而不是再维护两份编辑表单。
- 流程主操作与当前任务处理区位于画布缩放范围之外，正常Mac窗口无需拖到巨幅画布远端才能继续。
- 1440×900及1280×800视口检查：当前步骤、主按钮、阻断处理可见；长正文可滚动/放大；不要为了适应画布把关键操作缩得难读。

## 5. 禁用原因与操作入口的统一原则

不是为每个按钮多加一个 Tooltip 就算完成。

对当前推荐操作返回或派生：
- 是否可执行。
- 具体缺失项。
- 对应对象。
- 应去哪处理/调用哪个已有操作。

可复用一个轻量UI selector/映射模块；后端资格仍是最终依据。缺少只读资格数据时可补最小查询接口，但禁止把页面导航做成第二个后端工作流引擎。

例如：

- “还没有选择执行账号” → “选择账号”。
- “剧本有未保存修改” → “保存并分析”。
- “方案还未确认” → “查看并确认方案”。
- “小伙伴参考图尚未确认” → “查看这张图片”。
- “本次会话尚未检查图片入口” → “检查入口”。
- “本镜尾帧还未生成” → “去制作尾帧”。
- “有一条本目标新候选待选择” → “对比并采用”。

有能力等待、有内容错误、有人工操作是不同状态，不都显示“失败”。

## 6. 发送机制边界

本轮是用户流程修复，不再把开发重点扩大成VPN、网络或自动点击专项。

先读取当前实际发送方式，不擅自假定已经完成“普通Chat人工发送＋自动收取”。

- 当前仍为自动发送：主按钮明确为“开始生成提示词”，显示实际执行、等待、阻断及人工处理；保留已有自动链，不在本轮为追求成功盲目重发。
- 当前已有正式人工发送方式：准备完成后明确“请在右侧豆包点击发送”，定位绑定账号和会话，用户发送后自动读取、保存、回填。不要让用户复制JSON或点多道技术确认。
- 仅讨论过但尚未实现的人工发送不能只改按钮文案冒充交付。需要新增该能力时单列实际缺口，保留真实执行方式；不因此阻塞其他UI修复。

页面逻辑必须明确现在是工具在处理还是等待用户。不得暗中同时启动两套发送器，也不把页面切换、展开卡片当作发送授权。

## 7. 必须通过真正的前端验收

### 7.1 先做当前版本的可见流程复现

在用户本机可运行环境中启动真实 Electron 应用，使用实际窗口/浏览器工具抓取并查看截图。

从未打开短剧/新建短剧开始，沿正常按钮输入原故事。每走一步记录：

**看见什么 → 点了哪个可见控件 → 页面反馈什么 → 下一步从哪里进入。**

本轮截图只用当前真实窗口。不能把旧截图、静态HTML、设计稿或未连接业务的演示页面当作产品验收。

### 7.2 唯一业务样本仍为用户原故事与五镜头

- 在当前项目记录中找到用户原五镜头项目和原故事，保留用户成果。
- 用同一故事正常新建隔离测试项目，验证新用户从零开始。
- 既有原项目继续使用其5首帧、3尾帧、5视频提示词的对应关系测试。
- 新项目动态拆镜可以不是五个，不能为测试将产品镜数写死；仍使用同一故事，不另编用户看不懂的故事。
- 不硬编码某个项目ID、revision或历史任务ID。

### 7.3 UI验收不得通过后台跳步

下列方式可以用于单元测试或定位故障，但**不能计作用户流程通过**：

- `usePetStoryStore.getState().analyze()`、`continuePromptStage()`等直接调业务action。
- 直接调用 Electron IPC 写入、service方法或本地控制接口推进阶段。
- 手工改 `project.json`、任务状态、approved或final。
- 从console触发组件onClick，绕过不可见/禁用控件。
- 把Collapse mock成全部展开后，断言HTML里有某个按钮。
- renderToStaticMarkup里发现文字，就认定实际页面用户能看到和点击。
- 通过隐藏DOM、强制显示、解除disabled等操作推进流程。

真正UI验收：通过用户可见控件点击、输入、文件选择、确认及正常导航。UI自身调用原有store/服务是正常的；禁止的是测试代码替用户绕过UI。

只读读取项目/任务/请求记录用于核对证据是允许的，但不能用它修改或推进状态。

### 7.4 业务验证路径

A. 从空项目开始：选择账号 → 输入原剧本 → 分析 → 看到结果 → 采用/确认 → 基础素材提示词 → 选图/确认 → 关键帧 → 视频 → 结果。

B. 打开原五镜头项目：根据真实缺项定位下一步；已有成果不重做；候选可比较采用；局部失败能够从当前页处理。

C. 用同一项目验证可用性：
- 可选链接为空仍可走剧本流程。
- 未选账号有可点击处理入口。
- 任一步待保存能定位到具体字段，保存后能继续。
- 未完成前置条件时显示真实原因及跳转，不只是灰按钮。
- 新候选存在但用户手改保留时不误计全部完成。
- 一个基础素材批次完成不把整个短剧显示为完成。
- 当前入口检查失效后，在当前操作旁能重新检查。
- 失败、只读恢复、结束等待后页面说明仍准确。
- 重开不会自动生成请求，能回到合理位置并保留成果。
- 来回导航和画布缩放不卸载账号Webview、不丢会话、不重复发送。

本轮允许通过已登录的豆包普通Chat做必要真实文字验证。所有正文必须来自正常页面触发的豆包回复，不让Codex人工写稿注入。

图片美术接受与实际媒体生成沿用用户确认边界：用户已经授权并确认的素材/任务可走正常页面验证；缺少确认或媒体授权时，停在对应**真实可见的人工交接点**，记录待用户操作，不自动批准、不批量抽卡。未完成真实媒体步骤要标“待人工媒体验收”，不能说已端到端通过。

若发送或平台故障阻断，前端流程修复仍要完成。可用原项目已有真实回复与媒体检查展示，但不能拿它顶替新项目真实生成成功。离线平台模拟可以验证交互，必须单独标记，不能算真实豆包验收。

## 8. 工程与测试要求

保留必要的单元/集成测试，新增以DOM可见性和实际点击为依据的交互测试，使用当前合适的Electron/浏览器测试工具。不要为了本轮换整个技术栈。

需要覆盖：
- 当前阶段及下一步推导与实际项目状态一致。
- 关键动作的前置原因和直接处理按钮一致。
- 从头创建后分析完成可以看到结果和下一步。
- 未保存草稿在切页、保存、恢复中的处理。
- 素材阶段不依赖隐藏制作控制。
- 原有单项服务与新主入口共用，不重复生成。
- 候选、采用、确认和完成计数不混用。
- 失败处理按钮实际可见且可点。
- 旧项目与已完成素材正常恢复。
- 真实Webview保活不退化。

现有静态渲染测试仍可保留，但明确不属于可见流程验收。不要删除失败测试、放宽生成资格或写入假数据换取通过。

执行相关类型检查、Lint、构建和当前适用测试。依赖/外部平台阻断分别记录；本轮不要求重构无关模块或解决所有历史警告。

## 9. 实施次序和完成要求

按以下顺序连续推进，不反复要求用户确认已经明确的方向：

1. 当前真实界面走查、源码入口映射，确认UX01～UX11仍存在的部分。
2. 统一主路径、阶段状态与下一步主操作；修复直接剧本入口和方案完成交接。
3. 接通素材、关键帧、视频各阶段的前置处理和明确操作；保留现有画布。
4. 整理当前任务恢复、未保存提示、完成计数和非技术文案。
5. 从正常界面完成新项目与原五镜头两条验证，修复实测发现的断点。
6. 截图/操作记录、实际技术测试、报告和普通启动交付。

没有历史六小时/P4时间限制，但不扩大本轮业务范围。不新建第二套生产调度、存储或提示词框架。

输出 `docs/USER_JOURNEY_REPAIR_REPORT.md`，至少包含：
- UX01～UX11哪些确认存在、怎样修复、实际修改文件。
- 六阶段的可见入口、主按钮、前置条件和结果页面。
- 新旧入口的功能去向表，证明未丢失原功能。
- 真实点击走查表与截图位置；离线UI测试、真实Chat、真实媒体分别列出。
- 仍需要用户操作或外部条件的具体步骤。
- 准确启动命令。

每一步走查记录建议使用：
`步骤 | 页面可见状态 | 用户点击的真实控件 | 页面反馈 | 下一步入口 | 证据 | 通过/阻断/未测试`

截图和私有请求证据保存在本地ignored目录，未获授权不上传。启动应用供用户检查；不能声称未观察的GUI已验收。

不自动Git提交、推送、发布或归档其他变更，不进入P5。

**最终标准：用户不读开发文档、不看JSON、不知道store/service、不靠Codex后台调用，就能从输入剧本明确地走到当前已实现的逐镜素材结果。任何未完成步骤，都能从当前页面看懂原因并找到真实下一步。**
