这些记录能证明验证阻断了本次执行，不能证明豆包服务端为什么要求验证。没有服务端风控原因，不能把鼠标移动、DOM 点击、请求频率或某个提示词断定为触发原因，也不能保证以后永不出现验证。

已定位的客户端问题会放大失败或使流程无法恢复：

- 未确认提交的分支先抛出“提交不明”，后续验证检测无法执行，账号可能仍被当作就绪。
- 已确认受理后仍先等待验证检查，受理证据没有立即保存；验证优先级也可能被普通不明状态覆盖。
- 恢复任务在检查验证之前导航或刷新，可能打断用户正在完成的验证。
- 缺少原会话定位时，恢复先把任务标为正在观察，再退出页面执行，留下无法结束的假观察。
- 一律禁止显式重发，没有为“核对后仍然不明”的停止任务提供出口。

## 运行规则

1. 准备、上传、配置、发送及只读观察均识别实际可见验证层；聊天正文、隐藏验证框架和历史讨论不构成验证证据。
2. 发送前在同一页面脚本内再次检查验证，出现验证时零点击。发现验证立即暂停该账号任务并保留原运行，不自动刷新、解决验证或反复提交。
3. 用户在原账号完成验证后重新检测账号状态；仅真实页面就绪后才恢复。账号阻断不能被早先的过期就绪探测覆盖。
4. 平台受理证据一旦确认立即保存。普通“继续原制作任务／检查原制作结果”只核对原请求，缺少具体会话时保持暂停并指导用户定位历史会话。
5. 对已停止、没有明确结果且受理仍不明的原运行，显示“确认重发一次”。用户确认可能重复生成和再次消耗额度后，以原提交定位和新的授权 ID 创建关联请求。
6. 原任务及其提交意图、输入和迟到结果保留。明确重发后，原本地验证／确认等待状态收束为暂停，释放旧任务占位；这不取消平台请求，也不解除账号验证。新请求先保持 hold，完成项目绑定及正式门禁后才启动；重复点击、回复丢失或重启恢复复用同一关联请求。后续新请求若再次不明，仍需针对该新运行单独确认。

## 验证范围

离线行为测试覆盖验证识别与中断、账号阻断竞态、单次发送、原结果核对、显式重发、幂等与写盘失败、项目绑定、历史保留及迟到结果归属。测试不向真实豆包账号重复发送请求，不求解或规避人机验证。真实平台的验证策略和未来验证触发率仍无法由本地测试证明。
