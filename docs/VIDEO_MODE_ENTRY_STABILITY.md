# 视频模式入口稳定性修复

日期：2026-11-08。记录本次工作树的原因分析与验证，不代表版本已发布。

## 已复现的原因

1. 视频直接技能入口点击后，页面会异步重建已选技能和参数控件。旧逻辑等待 1.5 秒未见参数，就改走模式菜单流程，再次点击新挂载的模式触发器。离线执行正式序列化脚本时，3 秒冷激活被第二次动作打断，最终误报“视频模式菜单选项不可见”。图片分支此前已避免这个动作，视频分支仍保留旧逻辑。
2. 旧逻辑将模式选择和模型／参数就绪混在一起：参数尚未挂载时，即使视频技能已选也报入口失败；普通输入区的残留视频参数又可能被当成模式已经选中。两种状态判断相互矛盾。
3. 入口搜索使用全页短文本包含匹配、几何位置排序和多级候选猜选。菜单没有唯一归属时还会取最后一个目标。这样的选择不能证明操作的是当前输入区的目标技能。
4. 入口回调已有详细结果，但视频调用方仅保存固定一次尝试和耗时，界面再统一简化为“尚未准备好”，丢失了真实失败阶段和原因。

## 代码规则

- `creationModeEntry.ts` 使用唯一可见编辑器所属的共同 surface。engine 内部节点不能代替包含兄弟技能栏的共同输入区。
- 直接技能入口只选择一次，随后只观察目标技能的连续选中状态。异步重建不会触发第二次模式点击。
- 技能“更多”展开与模式菜单是各自明确的状态。只接受当前输入区的精确入口，以及模式触发器明确关联或本次动作新建的内嵌菜单；无关参数菜单不参与选择。多输入区、多入口或多菜单无法消歧时停止。
- 模式阶段只证明目标技能已稳定选中。模型、比例、时长、上传、输入与提交仍由正式流程分别核验；残留参数不能提供模式成功证据。移除了入口阶段后的固定动画等待。
- 未增加恢复、重试、备用入口或提交次数，未放宽登录、验证、素材归属和发送前回读要求。
- 诊断按固定枚举保存操作、采样次数、稳定次数、缺失控件和失败原因。画布和任务详情展示准确阶段，不保存原始 DOM、异常原文、提示词或会话内容。

## 验证边界

新回归在旧实现下 6 例中 5 例失败；重构后模式入口相关 5 个测试文件共 100 项通过。回归执行真实序列化脚本，覆盖冷激活、共同输入区重建、技能已选而参数晚挂载、残留参数、模式菜单、技能“更多”、无关菜单、歧义及单次动作。

完整 `pnpm run validate` 通过：219 个测试文件、4438 项测试全部通过，类型检查、Lint（0 错误、148 项既有警告）、工程规则与主进程／渲染进程构建通过。独立审查中复现的“参数菜单抢占模式入口”也已修正，原场景现只点击一次真正的视频入口并取得连续两次目标选中证据。

上述为离线 DOM／业务行为验证。真实平台的登录、人机验证、入口缺失或实际拒绝仍按原流程暂停，不据离线测试宣称所有平台变体均已验收。

## 后续首帧上传阻断（2026-11-08）

用户继续原视频后，模式、模型、比例、时长已通过真实页面回读，任务仍未写入提交时间。新的失败发生在上传准备：`first_frame` 被直接等同于原生独立首帧槽；已有统一图片上传适配仅接受 `first_last_frame` 两图。页面虽有可用的统一图片入口，等待逻辑仍拒绝，上传选择、回执验证、提交前素材回读和主进程持久化也有同一缺项。

修复统一这些阶段：逻辑模式继续为 `first_frame`，原引用继续为 `first`；当前页面统一入口实际上传一张首图时，物理绑定如实记录 `reference`。一图不要求 `multiple`，两图仍要求。上传准备和提交前同时回读当前已选视频技能，技能重建会重置连续稳定采样，不能凭残留视频参数放行。文件摘要、预览、素材次序、真实引用节点和最终全文校验保留；明确原生槽要求仍拒绝统一入口。没有新增模式切换、重写正文、清除任务、重试或额外发送路径。

新增单首帧 DOM 回归在修复前重现 5 项失败，包含用户同样的“独立首帧尚未就绪”报错；修复后上传／控件／镜头输入相关回归通过，并覆盖技能缺失、切成图片、多技能歧义及异步重建。真实 TaskService 的 157 项生产流程测试通过，新增验证准备失败后沿用原任务、单图 mention／plain 绑定、持久化与重开、提交前错绑和篡改拒绝。上述为离线验证，未主动消耗真实图片／视频生成额度。

本轮完整 `pnpm run validate` 通过：219 文件、4465 项测试，类型、Lint、工程规则和构建均通过。随后提取重复的视频输入区身份判断，消除新增复杂度警告；受影响的 3 文件 67 项测试、全部类型检查、相关 Lint 和渲染构建再次通过。开发应用已在无活动任务时重启加载主进程修改，原视频任务保持暂停、选图保留且尚未提交。

## 新对话准备与模式选择边界（2026-11-09）

用户后续原任务再次在 `video_entry` 停止：15 秒、148 次采样、零稳定样本、`not_found`，仍无提交证据。短时诊断在实际页面重现了相同的零动作等待。现场也确认 `mode-select-action-btn` 的外层是无 role 的 DIV，但它的“对话”菜单实际只提供聊天／电脑任务，不能作为视频技能菜单。没有为这个错误假设扩大 div 候选、模糊匹配或添加备用入口。

另一处确定的初始化问题是：图片／视频每次继续都强制导航新文档，即使当前已是官方精确根页、没有消息和草稿。这会销毁已经加载的技能区，重新进入异步挂载和布局测量；相同已就绪页面上的正式视频技能函数可取得连续选中证据，重复重建文档的准备则曾超时。原代码只为普通 Chat 做过空根页复用，并把复用与“退出媒体技能、聚焦普通 Chat”耦合。

现在媒体明确传递目标用途，严格回读唯一真实可见编辑器、共同输入区、零消息／草稿／生成／附件／已选文件／上传进度以及同文档、同几何的连续稳定空态后复用原根页。技能选择仍由原函数执行。媒体准备不聚焦旧普通 Chat，不退出已选媒体技能。历史会话仍按正常流程导航一次；存在非本人草稿或附件时保留现场并停止，不以导航或清空作为恢复。旧图片恢复的精确本人草稿资格继续仅用于单次新文档导航，不能授权最终空态复用。

画布恢复条件同时与正式服务对齐：加入已有固定页面准备错误及发送前主动暂停／取消，保留任务／步骤／运行／账号、锁、活动执行和所有提交／受理／产物证据检查；新增媒体提交回执排除。真实账户验证仍由执行链重新检查，等待验证和受理不明继续走既有专门流程。没有人工清锁或直接修改任务文件。

### 执行状态与调度入口的进一步证据

正式原任务曾实际走过视频技能选择（7599 毫秒）、模型／比例／时长、单张首帧上传、原生正文写入和发送控件回读。主进程保存的真实绑定为一个 logical `first`、一个 physical `reference/plain`，具有文件摘要与预览证明，逻辑模式保持 `first_frame`；未记录提交意图或媒体提交收据。

该验收同时揭示了阶段写入缺陷：`setAccountAutomationState` 回传完整 runtime，归一化快照的 `chatAdjustmentGuard: undefined` 自有属性仍被结构化克隆保留，主进程正确拒绝其写入。就绪诊断是独立小补丁，仍能落盘，因而形成“stage 留在 preparing_account、readiness 已到 submission_controls”的矛盾记录。阶段上报改为自身字段白名单，并增加 `expectedRunId` 在任何写入前拒绝迟到旧运行；阶段展示不创建提交时间。主进程保护字段与提交证据规则保持不变。节流仅在成功回读后记录，旧阶段回执不影响后来状态。

先前验收按旧 stage 等待参数阶段未果，最后触发安全暂停；控制器中止后发送准备拒绝是预期停止，不能据此认定发送控件故障。取消分类现保留 `AbortError`，不再误报页面控件不稳定。没有修改发送定位、正文一致性或单次发送权限。

随后正式恢复暴露了另一项调度缺口：生产媒体仅在画布专用 callback 中绑定步骤运行，通用队列／任务入口的共同门禁仅覆盖文字任务。通用队列先启动时会产生新 task run、旧 step run 的不一致；迟到的旧启动失败又只按项目 ID 暂停，可能停止同项目新一轮。现已把生产媒体绑定放入共同派发门禁，所有入口均先取得原制作授权、绑定同 task/run 并回读，再发布页面执行映射。每一制作轮次拥有独立授权序号，异步回调返回后重新核验，旧结果不能暂停或移交后来运行；基础素材图片操作则核验独立操作上下文。共同门禁拒绝发生在页面派发前，固定 `dispatch_not_ready` 可通过原任务正式恢复，未放宽主进程制作授权校验。

历史项目另有步骤尚未写入 runId 的状态。画布仅在原任务、原步骤、当前运行历史、输入正文、编译引用、附件及视频配置全部一致，且无任何提交／受理／产物证据时提供正式恢复入口；非空而不同的 runId 仍拒绝。该判断只决定是否可请求主进程恢复，不能赋予执行权限，也不直接补写历史数据。

### 最终验证

完整 `pnpm run validate` 通过：224 个测试文件、4572 项测试，类型检查、Lint（0 错误、148 项既有警告）、工程规则及主进程／渲染进程构建均通过。新增行为测试覆盖真实 TaskService 阶段持久化、旧运行零写入、共同派发前绑定、并发启动及旧回调失效、正式暂停分类、无 runId 历史状态的严格恢复边界。

在原账号、原项目、原视频任务上，从画布正常点击“继续生成视频”实测：持久化阶段依次为 preparing_account、new_conversation、switching_mode、configuring，视频模式入口用时 4886 毫秒，随后参数回读通过。验收在参数配置阶段经正式本机接口主动暂停，最终为 paused／cancelled；任务和步骤 runId 一致，原选图保留，“继续生成视频”按钮可用。没有写入提交时间或媒体提交收据，没有发送视频生成请求。本次验证证明入口、参数与恢复调度已通过真实页面，不据此声称实际视频提交和生成已完成。

## 视频原对话丢失定位（2026-11-09 后续）

用户随后实际提交的视频请求进入 `submission_uncertain`，已有 submittedAt，却没有 conversationUrl、媒体收据或受理观察绑定。前述验收停在提交前，没有覆盖这段链路。

真实原账号历史中的服务器会话已核验：首帧附件与视频正文分成两条用户消息，后跟助手回复。正文含平台固定的视频参数外壳，剥离后与原任务完整正文逐字一致。旧视频链仅读取 DOM 和地址栏，没有接入图片已有的完整 provider 与媒体收据；默认单用户消息判断又把这两条消息判为 `user_ambiguous`。因此服务器已有原请求，应用却没有保存具体对话，画布的打开和检查入口同时被阻断。挂载中的一次 `conversation_identity_conflict` 是过渡采样，稳定 provider 结构本身没有变化，不需要猜测新结构或扩大 DOM 选择器。

视频现统一读取真实 provider，按原 task/run/account/submittedAt、完整输入和唯一原全文核验；已有收据则继续绑定原服务器消息 ID。前置空用户消息不靠猜测附件标记消除。媒体收据经正式 TaskService 校验写入并回读，不能用根页、临时路由、侧栏标题或最近会话替代。单次点击的本地 ACK 与平台受理分开：ACK 丢失仍进入原有只读受理窗口，不增加发送、重试或超时窗口。

已提交媒体缺少 URL 时，“进入豆包对话”请求正式只读定位，只有当前服务器消息证明原请求后才保存并显示。点击及异步返回均重新核验当前画布来源。用户明确重发后，新任务和原请求各有独立入口，原请求入口须匹配任务双向重发记录和制作步骤授权历史，不把旧对话伪装为新任务对话。

真实原任务已通过画布“原请求豆包对话”按钮保存具体会话和媒体收据，随后打开对应服务器会话。原 taskId、runId、submittedAt、暂停状态及任务数量均保持一致，未直接修改任务文件、未清锁、未新增或重发平台请求。显示浏览器另触发了可见性自动同步刷新；现已对当前仍未解决的已提交媒体会话精确保留现场，普通 Chat、其它会话和用户显式刷新不受此保护影响。持久化收据和当前具体路由一致时，直接显示原页，不要求虚拟列表中已卸载的历史正文重新出现。

最终完整 `pnpm run validate` 通过：227 个测试文件、4665 项测试，类型、Lint（0 错误、148 项既有警告）、工程规则和主进程／渲染进程构建全部通过。实际原任务验证已保存的会话、服务器消息与当前页面相符，进入浏览器和重复打开同一会话均未刷新文档；恢复定位没有改变原提交或产生重发。本节验证的是原对话定位、持久化和打开，不将原助手回复或会话地址等同于视频已经生成。
